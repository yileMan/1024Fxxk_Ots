## 1. 规划目标

本规划把 OTS V1 拆成可独立提案、设计、实现、测试和归档的 OpenSpec change。拆分遵循以下原则：

1. **纵向切片**：除纯工程基线外，每个 change 必须同时交付后端能力、前端入口和端到端验收，不把同一功能拆成长期分离的“后端任务”和“前端任务”。
2. **依赖单向**：基础设施 → 身份与主数据 → 离线交换 → 评估闭环 → 查询交付；后续模块只能依赖已归档的前置能力。
3. **复杂模块继续拆分**：离线导入、CVSS、评估状态机、自动复评分别拆成多个 change，避免单个 Spec 同时修改过多核心规则。
4. **数据库基线稳定**：V1 只使用方案定义的 11 张应用基础表，不为通知、工作台、采集范围、导入错误或任务队列增加业务表。
5. **每个 change 可验收**：proposal 必须列出需求编号；specs 使用 Given/When/Then 场景；tasks 必须包含数据、后端、前端、测试和文档检查项。
6. **范围克制**：邮件、AI 生成、跨产品评估复制、历史 CSV 自动映射不进入 V1 核心任务。

## 2. 开发前架构决策门

以下决策应在第一个 OpenSpec change 中固定，后续不得由单个功能 Spec 随意改变。

### ADR-01：数据库迁移方式

- **已确认**：使用编号化 MySQL SQL 脚本管理数据库升级，使数据库升级包与后端应用解耦。
- 后端可使用 SQLAlchemy 进行 ORM 和事务访问；升级脚本使用 `migrations/001_*.sql` 形式，按编号顺序执行并提供对应回滚说明。
- 不使用 Alembic，不在业务库创建 `alembic_version`；数据库基础表数量保持为 11。

### ADR-02：外部数据服务边界

- **已确认**：外网采集属于独立的外部数据服务，不是本项目的前端或后端开发范围。
- 本项目只负责导出采集范围，并接收符合版本化 ZIP/CSV 契约的输入数据包；不实现 NVD、CISA KEV 或 endoflife.date 的联网访问、匹配算法、采集游标或采集日志。
- 外部服务不得访问内网数据库或调用本项目的业务接口；双方仅通过离线文件契约交换数据。

### ADR-03：EOL 候选与确认记录

- V1 不新增 EOL 候选表。
- 候选、来源和确认结果保存在 `import_batch.manifest_json/result_json` 的版本化结构中，当前采用结论保存在 `ots_component.is_eol`，确认写入 `audit_log`。
- `ots-19-eol-review` 必须在 design 中给出 JSON Schema、重复候选规则和历史追溯方式，确认该方案可以满足“待确认、确认、不采信、来源冲突”验收。

### ADR-04：本地认证形式

- V1 不新增会话表。
- 登录只校验用户名和密码，不校验账号状态、密码规则或请求来源。
- 登录成功后使用仅包含用户 ID 的未签名 `ots_user_id` Cookie；不设置固定时效或令牌。
- 后续请求按 Cookie 中的用户 ID 读取角色和产品范围，用于授权与审计操作者识别。
- 禁止把密码、长期令牌或产品授权明文放入浏览器存储。

### ADR-05：前端技术基线

- 当前前端是 Vue 3 JavaScript 空工程，方案要求 Vue 3 + TypeScript + 管理端组件库。
- 在平台基线 change 中一次性迁移到 TypeScript、确定组件库和 API 类型生成方式；后续 Spec 不再混用 JavaScript 与 TypeScript。

## 3. OpenSpec 执行约定

### 3.1 Change 生命周期

每个任务使用下表中的 change ID：

```powershell
openspec new change <change-id>
openspec status --change <change-id>
openspec validate <change-id> --strict --no-interactive
```

推荐执行顺序：

1. `proposal`：说明目的、范围、不做什么、影响的需求编号和依赖 change；
2. `specs`：按 capability 编写新增/修改需求与 Given/When/Then 场景；
3. `design`：固定数据变更、API、权限、状态机、前端交互、失败处理和回滚方式；
4. `tasks`：依次列出测试、数据/后端、前端、集成和文档任务；
5. 实现前执行严格校验，实现后执行前后端测试和业务场景验收；
6. 验收通过后归档 change，使 delta specs 合并到主 specs；
7. 更新本文档对应任务状态和完成证据。

### 3.2 每个业务 Change 的固定交付结构

每个业务 change 的 `tasks.md` 至少包含：

```markdown
- [ ] 契约：需求场景、API 请求/响应、错误码、权限和状态转换
- [ ] 数据：表/字段/索引影响、事务、幂等、审计和迁移脚本
- [ ] 后端：路由、Schema、Service/Repository、授权和异常处理
- [ ] 前端：路由、页面/组件、API 类型、加载/空状态/错误状态和权限反馈
- [ ] 测试：后端单元/集成、前端组件、至少一个纵向业务场景
- [ ] 验收：OpenSpec strict validation、构建、覆盖率和需求追溯更新
```

纯工程 change 可以没有业务页面，但必须提供前后端集成验证界面或可观察结果；不能以“后续前端再做”为完成条件。

### 3.3 Definition of Done

一个 change 只有同时满足以下条件才能标记完成：

- [ ] proposal、specs、design、tasks 全部完成且 `openspec validate --strict` 通过；
- [ ] 后端 API、前端页面和数据迁移在同一 change 中可用；
- [ ] 权限拒绝、空数据、非法输入、并发冲突和服务失败至少覆盖相关场景；
- [ ] 后端与前端新增代码覆盖率均不低于 80%，核心状态机和计算器按场景全覆盖；
- [ ] OpenAPI 契约与前端 TypeScript 类型一致，不手写两套不一致的数据模型；
- [ ] 关键写操作与 `audit_log` 同事务提交，失败回滚不产生审计记录；
- [ ] 需求编号、测试证据、迁移和回滚说明已写入 change；
- [ ] change 已归档，本文档状态及完成提交号已更新。

**前端**：导入预览增加 KEV 和 EOL 候选区域，展示来源、日期、冲突和“待确认”标识，不把缺失数据解释为未 EOL。

**验收**：无关 KEV 被拒绝；EOL 无数据保持未知；单 OTS 失败不影响其他 OTS 且不推进其覆盖时间。外部服务如何拉取 KEV/EOL 数据不属于本项目验收。

**需求映射**：FR-EXCH-004、FR-EXCH-005、FR-EXCH-007、FR-EXCH-015、FR-VULN-004、FR-EOL-002、FR-EOL-003。

#### [ ] OTS-10 `ots-10-transactional-import-and-task-generation`（复杂度：XL，依赖：OTS-03/04/07/08/09）

**目标**：事务导入漏洞与候选匹配，并为相关产品版本直接生成独立评估任务。

**后端/数据**：创建 `vulnerability`、`vulnerability_ots_match`、`product_assessment`；批次幂等；CVE/匹配内容哈希；批量 upsert；失败回滚；逐 OTS 覆盖推进；按有效 `product_ots` 创建 `pending` 任务；导入只写一条 `batch_upsert` 审计摘要。

**前端**：完成导入向导“确认导入 → 查看结果”；显示批次状态、统计、覆盖结果、生成任务数量、失败摘要和重试入口。

**验收**：重复批次/相同包不重复数据和任务；一个候选 OTS 为多个产品版本生成独立任务；导入失败没有半成品；已完成评估不被覆盖。

**拆分限制**：该 change 内部 tasks 必须按“批次事务 → 漏洞事实 → 候选匹配 → 任务生成 → 覆盖时间”五个子阶段提交和验证，但统一作为一个原子业务 Spec 验收。

**需求映射**：FR-EXCH-009、FR-EXCH-010、FR-EXCH-011、FR-MATCH-002、FR-MATCH-003、FR-MATCH-004、FR-MATCH-005、FR-MATCH-006、FR-VULN-001、FR-VULN-002、FR-VULN-006。

### M3：漏洞评估、审核与复评

#### [ ] OTS-11 `ots-11-vulnerability-catalog-and-workbench`（复杂度：L，依赖：OTS-10）

**目标**：提供漏洞/候选匹配查询和按当前用户实时计算的工作台待办。

**前端**：工作台数量卡片和过滤跳转；漏洞列表/详情；来源事实、CVSS、CWE、KEV、范围、引用和候选依据分区展示。

**验收**：导入成功后负责人无需刷新任务表即可查询到待办；审核人只看到指定版本的 submitted 项；候选关系不显示为受影响结论。

#### [ ] OTS-12 `ots-12-assessment-editor-core`（复杂度：L，依赖：OTS-11）

**目标**：实现产品评估草稿的核心业务字段，不含最终提交动作。

**验收**：只有当前负责人可编辑；`not_affected/accept_risk/no_action` 等条件必填依据；并发修改提示刷新，不静默覆盖。

**需求映射**：FR-ASSESS-001、FR-ASSESS-003、FR-ASSESS-004、FR-ASSESS-006、FR-ASSESS-007、FR-ASSESS-008、FR-ASSESS-009、FR-ASSESS-010、FR-ASSESS-012。

#### [ ] OTS-13 `ots-13-cvss31-environmental-scoring`（复杂度：L，依赖：OTS-12）

**目标**：完成 CVSS v3.1 产品环境指标、服务端计算和展示。

**预留边界**：数据表保留 CVSS v4.0 相关字段和索引，但 V1 不导入、不写入、不通过 API 返回、不在前端展示，也不创建 v4.0 OpenSpec change。

**前端**：v3.1 指标表单、来源向量、实时预览、来源未提供提示；保存指标而非仅保存显示分数。

**验收**：官方示例向量结果一致；前端篡改分数无效；来源未提供 v3.1 时明确提示，且不自动生成评分。

**需求映射**：FR-MASTER-007、FR-ASSESS-005、FR-VULN-002、FR-VULN-003，系统方案 6。

#### [ ] OTS-14 `ots-14-assessment-submit-and-review`（复杂度：L，依赖：OTS-05/12/13）

**目标**：实现评估提交、审核通过和审核退回的第一版完整闭环。

**后端**：`/submit`、`/approve`、`/return` 动作接口；提交时完整校验并冻结修订；仅当前指定审核人可审核；禁止提交人自审；保存实际提交人/审核人和时间。

**前端**：提交确认、审核区、通过/退回对话框、退回意见必填、按状态只读、角色与动作提示。

**验收**：pending → submitted → completed；退回操作不能直接改提交人结论；提交人与审核人相同则提交失败并提示重新分配。

**需求映射**：FR-REVIEW-001、FR-REVIEW-002、FR-REVIEW-003、FR-REVIEW-005、FR-REVIEW-006、FR-USER-005。

#### [ ] OTS-15 `ots-15-return-revision-resubmit`（复杂度：L，依赖：OTS-14）

**目标**：实现退回后的新修订、历史链和重新提交。

**后端**：退回时创建下一修订；原修订不可变；同事务切换 `is_current`；重新提交；历史修订查询；已完成记录修改必须新建修订。

**前端**：修订历史时间线、版本对比、退回意见、当前修订编辑、旧修订只读。

**验收**：任何时刻同一产品 OTS/CVE 只有一个 current；旧提交和审核信息不被覆盖；重新提交形成可追溯链。

**需求映射**：FR-REVIEW-004、FR-ASSESS-009，产品评估状态设计。

#### [ ] OTS-16 `ots-16-automatic-reassessment`（复杂度：XL，依赖：OTS-10/15）

**目标**：来源事实、候选依据或产品 OTS 上下文实质变化时生成待复评修订。

**后端**：比较漏洞和匹配内容哈希；区分实质变化与文字变化；处理 CVSS、范围、Rejected、KEV、关联变化；保留完成修订并创建 `reassess`；幂等防重复。

**前端**：工作台待复评卡片、复评原因、变化摘要、旧结论对比和重新提交入口。

**验收**：同一变化不重复生成复评；纯描述变化不自动建任务；已完成结论保留；各产品复评状态互不影响。

**需求映射**：FR-VULN-005、FR-MATCH-005、FR-REVIEW-004，系统方案 5.5。

#### [ ] OTS-17 `ots-17-cross-product-approved-reference`（复杂度：M，依赖：OTS-11/14）

**后端**：跨产品查询严格限定 `is_current=1/status=completed/review_decision=approved`；字段白名单；不得返回草稿、证据或审核意见。

**前端**：评估详情增加“其他产品参考”只读区域，标记仅供参考且不能一键覆盖当前结论。

**验收**：未完成/已退回/非当前修订不可见；敏感字段不出现在 API；查看参考不改变当前任务状态。

**需求映射**：FR-ASSESS-011、FR-REVIEW-001，关键业务规则 17。

#### [ ] OTS-18 `ots-18-eol-review`（复杂度：L，依赖：OTS-02/09/11）

**后端/数据**：按 ADR-03 固定候选 JSON Schema；待确认查询；确认/不采信动作；更新 OTS 当前结论；冲突重入待确认；审计确认变更。

**前端**：工作台待确认 EOL、候选详情、来源链接、确认/不采信、官方来源补充和未知状态。

## 8. 风险与控制

| 风险 | 等级 | 控制措施 |
| --- | --- | --- |
| 编号 SQL 脚本执行顺序或回滚失控 | 高 | OTS-00 固定 ADR-01；每个脚本必须有顺序、幂等检查、回滚说明和空库/升级库验证 |
| EOL 待确认没有独立表 | 高 | OTS-19 先验证 JSON Schema、幂等和历史追溯；不能满足时先修订数据基线 |
| 导入事务同时更新事实、匹配、覆盖和任务 | 高 | OTS-10 分五个内部阶段；使用真实 MySQL 集成测试和失败注入 |
| 自动匹配被误认为产品受影响 | 高 | API、页面和导出统一标记候选；禁止自动填充产品适用性 |
| 跨产品参考泄露草稿或内部证据 | 高 | OTS-18 后端字段白名单和越权测试；前端只读摘要 |
| ZIP 路径穿越、压缩炸弹和恶意字段 | 高 | OTS-07 文件数/大小/路径/表头白名单，解压前后双重限制 |
| 无任务表/消息队列导致后台状态复杂 | 中 | 仅使用单 worker + `import_batch` 状态；恢复动作必须幂等 |
| 外部数据服务输出不符合离线契约 | 中 | OTS-07～09 固定版本化 Schema、样例包和兼容性校验；不在本项目实现采集逻辑兜底 |
| 前后端契约漂移 | 中 | OpenAPI 生成 TypeScript 类型；契约变更必须与页面在同一 change 合并 |
| 10 年数据增长影响查询 | 中 | OTS-19 对关键查询执行 EXPLAIN；OTS-23 使用代表性数据压测 |

## 9. V1 后置 Backlog（本轮不开发）

以下项目只有在 OTS-23 验收完成后，才分别创建新的 OpenSpec change：

- 邮件通知；
- 基于公开 CVE 事实的 AI 通用建议生成；
- 跨产品评估复制为目标产品草稿；

任何后置功能都不得绕过产品负责人独立评估、审核人审核、禁止自审、产品范围授权或审计规则。
