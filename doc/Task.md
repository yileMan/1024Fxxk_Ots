## 1. 规划目标

本规划把 OTS V1 拆成可独立提案、设计、实现、测试和归档的 OpenSpec change。拆分遵循以下原则：

1. **纵向切片**：除纯工程基线外，每个 change 必须同时交付后端能力、前端入口和端到端验收，不把同一功能拆成长期分离的“后端任务”和“前端任务”。
2. **依赖单向**：基础设施 → 身份与主数据 → 离线交换 → 评估闭环 → 查询交付；后续模块只能依赖已归档的前置能力。
3. **复杂模块继续拆分**：离线导入、CVSS、评估状态机、自动复评分别拆成多个 change，避免单个 Spec 同时修改过多核心规则。
4. **数据库基线稳定**：V1 只使用方案定义的 11 张应用基础表，不为通知、工作台、采集范围、导入错误或任务队列增加业务表。
5. **每个 change 可验收**：proposal 必须列出需求编号；specs 使用 Given/When/Then 场景；tasks 必须包含数据、后端、前端、测试和文档检查项。
6. **范围克制**：邮件、AI 生成、跨产品评估复制、历史 CSV 自动映射不进入 V1 核心任务。

## 2. 开发前架构决策门

以下决策应在第一个 OpenSpec change 中固定，后续不得由单个功能 Spec 随意改变。

### ADR-01：数据库迁移方式

- **已确认**：使用编号化 MySQL SQL 脚本管理数据库升级，使数据库升级包与后端应用解耦。
- 后端可使用 SQLAlchemy 进行 ORM 和事务访问；升级脚本使用 `migrations/001_*.sql` 形式，按编号顺序执行并提供对应回滚说明。
- 不使用 Alembic，不在业务库创建 `alembic_version`；数据库基础表数量保持为 11。

### ADR-02：外部数据服务边界

- **已确认**：外网采集属于独立的外部数据服务，不是本项目的前端或后端开发范围。
- 本项目接收包含 NVD 原始漏洞事实及受影响软件/版本范围的版本化 ZIP/CSV 数据包；采集范围导出可继续作为外网工具的可选辅助输入，但不是 NVD `1.0` 回传包的一部分。
- 外部服务不接收或回传内网 `ots_id`，不负责 OTS/CVE 候选匹配；平台导入漏洞事实后，按内部 OTS 名称、版本和后续确认的标识规则完成候选匹配。
- 本项目不实现 NVD、CISA KEV 或 endoflife.date 的联网访问、采集游标或采集日志；KEV/EOL 是否启用另行确认，启用时升级包格式版本。
- 外部服务不得访问内网数据库或调用本项目的业务接口；双方仅通过离线文件契约交换数据。

### ADR-03：EOL 候选与确认记录

- V1 不新增 EOL 候选表。
- 候选、来源和确认结果保存在 `import_batch.manifest_json/result_json` 的版本化结构中，当前采用结论保存在 `ots_component.is_eol`，确认写入 `audit_log`。
- `ots-19-eol-review` 必须在 design 中给出 JSON Schema、重复候选规则和历史追溯方式，确认该方案可以满足“待确认、确认、不采信、来源冲突”验收。

### ADR-04：本地认证形式

- V1 不新增会话表。
- 登录只校验用户名和密码，不校验账号状态、密码规则或请求来源。
- 登录成功后使用仅包含用户 ID 的未签名 `ots_user_id` Cookie；不设置固定时效或令牌。
- 后续请求按 Cookie 中的用户 ID 读取角色和产品范围，用于授权与审计操作者识别。
- 禁止把密码、长期令牌或产品授权明文放入浏览器存储。

### ADR-05：前端技术基线

- 当前前端是 Vue 3 JavaScript 空工程，方案要求 Vue 3 + TypeScript + 管理端组件库。
- 在平台基线 change 中一次性迁移到 TypeScript、确定组件库和 API 类型生成方式；后续 Spec 不再混用 JavaScript 与 TypeScript。

## 3. OpenSpec 执行约定

### 3.1 Change 生命周期

每个任务使用下表中的 change ID：

```powershell
openspec new change <change-id>
openspec status --change <change-id>
openspec validate <change-id> --strict --no-interactive
```

推荐执行顺序：

1. `proposal`：说明目的、范围、不做什么、影响的需求编号和依赖 change；
2. `specs`：按 capability 编写新增/修改需求与 Given/When/Then 场景；
3. `design`：固定数据变更、API、权限、状态机、前端交互、失败处理和回滚方式；
4. `tasks`：依次列出测试、数据/后端、前端、集成和文档任务；
5. 实现前执行严格校验，实现后执行前后端测试和业务场景验收；
6. 验收通过后归档 change，使 delta specs 合并到主 specs；
7. 更新本文档对应任务状态和完成证据。

### 3.2 每个业务 Change 的固定交付结构

每个业务 change 的 `tasks.md` 至少包含：

```markdown
- [ ] 契约：需求场景、API 请求/响应、错误码、权限和状态转换
- [ ] 数据：表/字段/索引影响、事务、幂等、审计和迁移脚本
- [ ] 后端：路由、Schema、Service/Repository、授权和异常处理
- [ ] 前端：路由、页面/组件、API 类型、加载/空状态/错误状态和权限反馈
- [ ] 测试：后端单元/集成、前端组件、至少一个纵向业务场景
- [ ] 验收：OpenSpec strict validation、构建、覆盖率和需求追溯更新
```

纯工程 change 可以没有业务页面，但必须提供前后端集成验证界面或可观察结果；不能以“后续前端再做”为完成条件。

### 3.3 Definition of Done

一个 change 只有同时满足以下条件才能标记完成：

- [ ] proposal、specs、design、tasks 全部完成且 `openspec validate --strict` 通过；
- [ ] 后端 API、前端页面和数据迁移在同一 change 中可用；
- [ ] 权限拒绝、空数据、非法输入、并发冲突和服务失败至少覆盖相关场景；
- [ ] 后端与前端新增代码覆盖率均不低于 80%，核心状态机和计算器按场景全覆盖；
- [ ] OpenAPI 契约与前端 TypeScript 类型一致，不手写两套不一致的数据模型；
- [ ] 关键写操作与 `audit_log` 同事务提交，失败回滚不产生审计记录；
- [ ] 需求编号、测试证据、迁移和回滚说明已写入 change；
- [ ] change 已归档，本文档状态及完成提交号已更新。

## 4. 总体里程碑与进度

状态标记：`[ ] 未开始`、`[~] 进行中`、`[x] 已完成`、`[!] 阻塞`。

#### [x] OTS-07 `ots-07-package-contract-and-validation`（复杂度：L，依赖：OTS-06，仅复用其 `import_batch` 表）

**目标**：固定 NVD 原始事实的两文件 ZIP/CSV 契约，完成上传、校验、真实数据库预览和事务确认导入。

**后端/数据**：格式 `1.0` 根目录只包含 `manifest.csv` 和一行一个 CVE 的 `nvd_cves.csv`；CVE 行保存来源标识、状态、时间、描述、全部 CVSS/CWE/参考、原始 configuration，以及归一化的受影响软件和精确版本/版本范围。创建第 8 张表 `vulnerability`（下一迁移 `010_vulnerability.sql`），按 `cve_id` 分类并事务 upsert；复用 `import_batch` 记录状态、结果和幂等，整批成功时写一条 `batch_upsert` 审计。外部包不包含 `collector_scope.csv`、`matched_ots_json` 或内网 `ots_id`。

**前端**：工作台待复评卡片、复评原因、变化摘要、旧结论对比和重新提交入口。

**验收**：同一变化不重复生成复评；纯描述变化不自动建任务；已完成结论保留；各产品复评状态互不影响。

**需求映射**：FR-VULN-005、FR-MATCH-005、FR-REVIEW-004、FR-WORK-001，系统方案 5.5。

**需求追溯**：FR-VULN-005 由来源状态、CVSS v3.1 和规范化受影响范围的基线差异触发覆盖；FR-MATCH-005 由候选新增、更新、移除及跨入口指纹幂等覆盖；FR-REVIEW-004 由统一修订克隆原语、历史完成修订不可变、连续父子链和重新提交覆盖；FR-WORK-001 由 `reassess` 当前修订实时进入负责人工作台及待办覆盖。系统方案 5.5 的实质变化矩阵、纯文字零复评、产品独立性和关联停用/恢复均有后端、前端及 Chrome 场景证据。

**完成证据**：迁移 `013_automatic_reassessment.sql` 在既有 11 张基础表上增加评估基线/变化摘要和产品 OTS 软状态，不新增表；`initialize-assessment-bases` 支持 dry-run、稳定分页、中断恢复和幂等重跑，初始化未完成时自动入口拒绝评估写入。来源确认、候选执行和关联状态变更统一比较规范基线，完成态创建单一 `reassess` 子修订，进行中状态合并变化并递增 `row_version`，审计仅保存入口、数量、变化类型、父子修订和指纹。后端 pytest 209 项通过、总覆盖率 93%，自动复评核心模块覆盖率 93%～100%；MySQL 8.0.39 验证迁移、初始化恢复、双会话竞争、两产品独立与连续修订链。10,000 条任务规划耗时 1.585 秒、峰值 18.83 MiB。前端 Vitest 125 项通过，语句覆盖率 96.87%、分支 80.66%、函数 83.68%，类型检查和生产构建通过；系统 Chrome Playwright 全量 31 项及新增纵向场景通过。OpenAPI/TypeScript 连续生成哈希一致，主规格同步后 OpenSpec 全量严格校验通过。OpenSpec change 于 2026-09-05 归档为 `2026-09-05-ots-16-automatic-reassessment`。NVD `1.0` 未提供可信 KEV/EOL 输入，因此 V1 基线明确不把缺失 KEV 当作 `false`，EOL 仍由 OTS-18 处理。

#### [ ] OTS-17 `ots-17-cross-product-approved-reference`（复杂度：M，依赖：OTS-11/14）

**目标**：评估时只展示相同 OTS/CVE 在其他产品已审核通过的当前摘要。

**后端**：跨产品查询严格限定 `is_current=1/status=completed/review_decision=approved`；字段白名单；不得返回草稿、证据或审核意见。

**前端**：评估详情增加“其他产品参考”只读区域，标记仅供参考且不能一键覆盖当前结论。

**验收**：未完成/已退回/非当前修订不可见；敏感字段不出现在 API；查看参考不改变当前任务状态。

**需求映射**：FR-ASSESS-011、FR-REVIEW-001，关键业务规则 17。

#### [ ] OTS-18 `ots-18-eol-review`（复杂度：L，依赖：OTS-02/09/11）

**目标**：审核人确认或不采信 EOL 候选，并处理来源冲突。

**后端/数据**：按 ADR-03 固定候选 JSON Schema；待确认查询；确认/不采信动作；更新 OTS 当前结论；冲突重入待确认；审计确认变更。

**前端**：工作台待确认 EOL、候选详情、来源链接、确认/不采信、官方来源补充和未知状态。

**验收**：无可靠信息不推断未 EOL；官方来源优先；重复候选幂等；历史批次可追溯确认结果。

**需求映射**：FR-EOL-001、FR-EOL-002、FR-EOL-003，系统方案 5.4。

### M4：查询、导出、审计与交付

#### [ ] OTS-19 `ots-19-global-search-and-traceability`（复杂度：L，依赖：OTS-16/17/18）

**目标**：完成跨 CVE、OTS、产品、状态、严重度、KEV 和时间的组合查询及追溯链。

**后端**：统一分页/排序/筛选；CVE → 最近批次 → 候选匹配 → 产品评估/修订 → 审核的追溯接口；查询索引验证。

**前端**：漏洞评估组合查询、可分享筛选参数、追溯详情和清晰空状态。

**验收**：产品范围裁剪正确；常用查询使用既定索引；正常规模 95% 请求小于 3 秒。

**需求映射**：FR-WORK-003、FR-WORK-004，NFR 12.2。

#### [ ] OTS-20 `ots-20-assessment-export`（复杂度：M，依赖：OTS-14/19）

**目标**：导出指定产品版本、指定 OTS 的完整评估表。

**后端**：导出任务、稳定列顺序、UTF-8、来源/环境评分、向量、依据、处置和审核信息；产品范围授权；大结果流式响应。

**前端**：数据交换－评估导出页；范围选择、导出确认、进度/失败反馈和下载。

**验收**：导出内容与当前已授权查询一致；未授权不可导出；导出行为不写数据库变更审计。

**需求映射**：FR-EXPORT-001、FR-EXPORT-002、FR-AUDIT-003。

#### [ ] OTS-21 `ots-21-audit-and-system-operations`（复杂度：L，依赖：OTS-02/10/15）

**目标**：完成数据库变更记录查询和系统运行信息页面。

**后端**：统一审计服务复核；只记录成功的 insert/update/delete/batch_upsert；审计查询只读；应用版本、数据库、磁盘、最近备份/导入/失败状态接口。

**前端**：系统管理－变更记录与运行状态页；对象、用户、动作、时间筛选；关键字段差异查看。

**验收**：失败事务无审计；登录、查询、导出、备份不入审计；普通用户不能修改/删除记录；运行状态故障可见。

**需求映射**：FR-AUDIT-001、FR-AUDIT-002、FR-AUDIT-003，系统方案 11.3。

#### [ ] OTS-22 `ots-22-deployment-backup-restore`（复杂度：L，依赖：OTS-21）

**目标**：形成可交付的单机部署、升级、备份、恢复和健康检查能力。

**后端/运维**：Docker Compose 的应用/MySQL 两个主要服务；非容器启动方式；初始化、升级、每日备份、恢复和健康脚本；持久化目录和结构化日志；不内置固定密码。

**前端**：运行状态页读取最近备份文件、大小、时间和结果；提供只读操作指引，不在页面执行高风险恢复。

**验收**：全新环境可初始化；备份可在隔离库恢复；升级脚本可重复检测；管理平台不主动访问互联网。

**需求映射**：NFR 12.1/12.3，系统方案 10、11。

#### [ ] OTS-23 `ots-23-v1-acceptance-hardening`（复杂度：XL，依赖：OTS-00～22）

**目标**：按 V1 验收标准执行端到端、性能、安全边界和恢复验证，关闭交付缺口，不新增范围外功能。

**后端**：10,000 行包导入、幂等/回滚、权限矩阵、20 并发、查询索引、文件安全、备份恢复测试与修复。

**前端**：六个一级导航、关键旅程 E2E、空/错/加载状态、二次确认、权限反馈、3 秒性能目标和使用说明。

**验收**：需求规格第 13 章 21 项全部有自动化或记录化证据；数据库基础表数量为 11；未配置邮件或 AI 时完整人工闭环可用。

**需求映射**：V1 验收标准 1～21，系统方案 13。

## 8. 风险与控制

| 风险 | 等级 | 控制措施 |
| --- | --- | --- |
| 编号 SQL 脚本执行顺序或回滚失控 | 高 | OTS-00 固定 ADR-01；每个脚本必须有顺序、幂等检查、回滚说明和空库/升级库验证 |
| EOL 待确认没有独立表 | 高 | OTS-19 先验证 JSON Schema、幂等和历史追溯；不能满足时先修订数据基线 |
| 漏洞事实导入、内部匹配和任务生成边界混淆 | 高 | 分别由 OTS-07、OTS-08、OTS-10 负责，并为每一步建立独立幂等键和集成测试 |
| 自动匹配被误认为产品受影响 | 高 | API、页面和导出统一标记候选；禁止自动填充产品适用性 |
| 跨产品参考泄露草稿或内部证据 | 高 | OTS-18 后端字段白名单和越权测试；前端只读摘要 |
| ZIP 路径穿越、压缩炸弹和恶意字段 | 高 | OTS-07 文件数/大小/路径/表头白名单，解压前后双重限制 |
| 无任务表/消息队列导致后台状态复杂 | 中 | 仅使用单 worker + `import_batch` 状态；恢复动作必须幂等 |
| 外部数据服务输出不符合离线契约 | 中 | OTS-07 固定 NVD `1.0` Schema、样例包和兼容性校验；KEV/EOL 启用时由 OTS-09 升级版本，不在本项目实现采集逻辑兜底 |
| 前后端契约漂移 | 中 | OpenAPI 生成 TypeScript 类型；契约变更必须与页面在同一 change 合并 |
| 10 年数据增长影响查询 | 中 | OTS-19 对关键查询执行 EXPLAIN；OTS-23 使用代表性数据压测 |
