# database-migration-foundation Specification

## Purpose

为 OTS 平台建立可重复执行、可追溯的 MySQL 数据库升级和事务访问基线，确保后续业务表变更在空库、升级库和失败恢复场景中具有一致结果。

## Requirements

### Requirement: MySQL 连接与事务边界
系统 SHALL 使用 MySQL 8.x、InnoDB 和 utf8mb4 建立数据库连接，并为每次业务写入提供明确的事务边界；事务失败 MUST 回滚其未提交变更。

#### Scenario: 成功的事务提交
- **WHEN** 一项数据库写入在事务内完成且没有错误
- **THEN** 系统提交该事务并使其变更可查询

#### Scenario: 事务内发生错误
- **WHEN** 数据库写入过程中发生约束错误或服务错误
- **THEN** 系统回滚该事务
- **AND** 客户端不会观察到该事务的部分写入结果

### Requirement: 编号化 SQL 迁移
系统 SHALL 按连续编号顺序执行 SQL 迁移脚本，并记录已执行版本；同一数据库再次执行迁移 MUST 不重复应用已成功执行的脚本。

#### Scenario: 空库初始化
- **WHEN** 运维人员对空数据库执行迁移命令
- **THEN** 系统按编号顺序执行全部待执行脚本并记录每个成功版本

#### Scenario: 已升级数据库再次执行
- **WHEN** 运维人员对已执行部分或全部脚本的数据库再次执行迁移命令
- **THEN** 系统仅执行尚未记录为成功的后续脚本
- **AND** 已执行脚本不会造成重复对象或重复数据变更

### Requirement: 迁移失败与回滚说明
每个 SQL 迁移 SHALL 具备对应的回滚说明；迁移执行失败时 MUST 停止后续脚本并报告失败版本，且不得把失败脚本标记为已完成。

#### Scenario: 单个迁移脚本失败
- **WHEN** 执行中的迁移脚本返回错误
- **THEN** 系统停止执行后续迁移并报告失败脚本编号
- **AND** 系统不把该脚本记录为成功执行

#### Scenario: 需要人工回退
- **WHEN** 运维人员依据迁移回滚说明处理首次上线失败
- **THEN** 回滚说明明确适用前提、执行顺序、数据影响和不可安全回滚时的向前修复要求

### Requirement: 平台基线不创建业务表
本 change SHALL 只交付迁移机制和验证样例，不得创建 `app_user`、`audit_log` 或其他 OTS 业务基础表。

#### Scenario: 验证平台基线迁移
- **WHEN** 在空库执行本 change 的迁移验证
- **THEN** 数据库只包含迁移机制所必需的元数据和非业务验证对象
- **AND** 不存在 OTS 业务基础表
