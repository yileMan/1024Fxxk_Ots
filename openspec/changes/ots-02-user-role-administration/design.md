## Context

参见 `proposal.md` 与 `specs/user-role-administration/spec.md`。`ots-01-local-authentication` 已归档并提供基于 `ots_user_id` Cookie 的当前用户解析；该身份中的当前角色将作为本 change 的管理员授权依据。`app_user`、`audit_log`、Argon2id 密码服务和编号化迁移已存在，且 `app_user` 已包含 `roles_json`、`status` 与 `row_version`。

本变更遵守 ADR-04：登录只验证用户名及密码，Cookie 仅传递用户 ID；不得在用户管理中重新引入 Cookie 签名/时效、账号状态校验、密码策略或请求来源校验。V1 固定为 11 张应用基础表。

## Goals / Non-Goals

**Goals:**

- 在既有认证基础上建立可复用的管理员授权依赖和用户管理 API。
- 以单事务保存 `app_user` 变更及脱敏的 `audit_log`，并通过 `row_version` 阻止静默覆盖。
- 让 Vue 管理页面可完整完成查询、编辑、重置密码和停用，并忠实呈现 API 的失败结果。

**Non-Goals:**

- 不创建或修改 `user_product_scope`，不实现产品/版本授权、负责人/审核人分配或自审规则。
- 不增加删除、启用恢复、自助改密、强制登出、账户锁定、密码规则、角色配置或认证安全附加校验。
- 不修改 OTS-01 已定义的 `local-authentication` 行为；用户 `status` 是供后续人员分配与历史保留使用的管理字段，本 change 不让它成为登录额外条件。

## Decisions

### 1. 以当前角色的 `admin` 成员资格执行服务端授权

新增 `require_admin` 依赖，在 OTS-01 的当前用户解析后检查 `roles_json` 是否包含 `admin`。所有 `/api/v1/users` 资源均经过该依赖；前端路由和菜单仅作体验控制，不能替代服务端拒绝。

不复用“前端隐藏按钮”或在各路由散落角色判断：前者不可阻止直接 API 调用，后者容易在后续资源扩展时产生不一致。

### 2. 用资源式 API 与独立密码/停用动作表达不同写入意图

统一使用 `/api/v1/users`：

| 接口 | 用途 | 成功结果 |
| --- | --- | --- |
| `GET /users` | 分页、筛选查询 | 用户页与总数 |
| `GET /users/{user_id}` | 读取编辑前的公开详情 | 公开用户 |
| `POST /users` | 创建用户 | `201` 及公开用户 |
| `PUT /users/{user_id}` | 更新显示名称和角色 | 公开用户 |
| `POST /users/{user_id}/reset-password` | 重置密码 | 公开用户 |
| `POST /users/{user_id}/disable` | 停用 | 公开用户 |

所有更新型请求携带 `row_version`；创建不携带版本。详情、列表和写入响应都使用同一公开用户 DTO，永不序列化 `password_hash`。稳定错误码至少区分 `AUTH_FORBIDDEN`、`USER_NOT_FOUND`、`USER_LOGIN_NAME_CONFLICT`、`USER_ROLE_INVALID`、`USER_VERSION_CONFLICT` 与字段校验错误，供前端选择正确提示。

将重置密码与停用拆成显式动作，而不是允许通用 `PUT` 任意修改敏感字段：表单意图清晰，审计详情可精确记录，且后续不会误把密码或状态纳入一般资料编辑。

### 3. 固定角色白名单与复用既有密码摘要服务

Schema 在请求进入 Service 前验证角色为非空去重数组，元素只能为 `admin`、`product_owner`、`reviewer`；数据库 JSON 约束继续作为最终防线。用户创建和重置密码都调用 OTS-01 的同一摘要服务，保持登录兼容；不在此处定义长度、复杂度或其他密码策略。

替代方案是新增角色表、权限矩阵或在角色 JSON 中保存自由文本。这些都会超出固定角色和 11 表约束，且会推迟后续 change 的人员选择一致性，因此不采用。

### 4. 使用带原版本号的条件更新实现乐观锁

Repository 对编辑、重置密码和停用执行等价于 `WHERE id = :id AND row_version = :expected_version` 的更新，并在成功时 `row_version = row_version + 1`。受影响行数为零时，Repository 再确认用户是否存在：存在则返回 `USER_VERSION_CONFLICT`，不存在则返回 `USER_NOT_FOUND`。已停用用户的停用操作先读取状态，直接返回当前公开用户而不写入。

不使用悲观锁或最后写入覆盖：前者对少量管理操作没有必要且拉长事务，后者会丢失角色或停用状态。

### 5. 用户与审计记录以同一事务提交，并对秘密字段脱敏

Service 在单个 SQLAlchemy 事务内执行用户写入和 `audit_log` 插入。审计对象为 `app_user`，动作按基础表约定为 `insert` 或 `update`；`detail_json` 记录显示名称、角色、状态和版本的变化。密码重置仅写入 `password_reset: true` 与版本变化，绝不保存明文、新旧摘要或可离线猜测的派生内容。若审计写入失败，用户修改一并回滚。

不在前端自行记录审计，也不将密码摘要写入“仅管理员可见”字段；前者无法保证原子性，后者仍扩大秘密暴露面。

### 6. 前端以列表为入口、受控表单为编辑界面

在系统管理下新增用户路由。列表拥有服务端分页和筛选、加载骨架、空状态、错误重试、创建入口及每行编辑/停用入口。编辑表单包含显示名称、固定角色多选、只读状态与版本号；密码仅通过独立重置表单输入，不回显也不缓存。停用必须弹出二次确认。

表单提交成功后以响应更新当前项并刷新需要失效的列表数据。收到 `USER_VERSION_CONFLICT` 时保留本地输入、提示刷新并从服务端重新获取详情；收到权限错误时转到明确的 403 反馈，不把 403 假装成空列表。

## Risks / Trade-offs

- [管理员可能将最后一个管理员移除 `admin` 角色或停用] → 本需求基线未规定“至少一名管理员”保护，因此不增加隐含业务规则；运维保留初始化管理员命令作为恢复路径，并在界面给出风险提示。
- [ADR-04 规定停用不参与登录校验，用户仍可使用匹配密码取得身份] → 本 change 将“停用”限定为保留历史和供后续人员分配筛选的状态变更；若需即时封禁，必须先单独修订 ADR-04 与 `local-authentication` 规格。
- [管理者并发编辑时需要手动刷新] → 保留未提交输入和明确冲突信息，避免静默丢失；不引入实时协作或长事务锁。
- [审计详情若包含秘密会造成持久化泄露] → 密码操作使用布尔标记并在单元/集成测试中断言审计、响应和日志均无密码/摘要。

## Migration Plan

1. 确认 `ots-01-local-authentication` 已归档，且现有 `app_user`、`audit_log`、密码摘要和当前用户依赖可用。
2. 本 change 不新增表或字段；对现有迁移执行空库及升级库检查，确认角色 JSON 约束、`row_version` 和审计索引已存在。
3. 发布后端 API 与 OpenAPI，再生成前端 TypeScript 类型并发布系统管理用户页面。
4. 以现有管理员验证创建、编辑、重置、停用、越权、冲突和审计场景。

回滚时下线用户管理路由和页面即可；不回滚已提交的用户或审计数据。若部署缺陷影响写入，采用向前修复，避免删除保留历史的用户记录。
