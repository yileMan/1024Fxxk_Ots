## Purpose

为 OTS 管理平台提供管理员可验证的本地用户与固定角色管理能力，保证后续人员分配、产品范围授权和审计能够基于受控且可追溯的用户记录执行。

## ADDED Requirements

### Requirement: 管理员访问控制
系统 MUST 仅允许当前用户角色包含 `admin` 的用户访问用户管理资源和页面；其他已登录用户及未登录访问者均不得读取或修改用户管理数据。

#### Scenario: 管理员访问用户管理
- **GIVEN** 当前用户具有 `admin` 固定角色
- **WHEN** 该用户查询、创建、更新、重置密码或停用本地用户
- **THEN** 系统执行对应的用户管理操作

#### Scenario: 非管理员被拒绝
- **GIVEN** 当前用户不存在或其固定角色不包含 `admin`
- **WHEN** 该用户直接请求用户管理 API 或访问系统管理用户页面
- **THEN** 系统拒绝访问且不返回用户列表、密码摘要或可编辑数据
- **AND** 请求不得写入用户记录或 `audit_log`

### Requirement: 分页查询本地用户
系统 SHALL 向管理员提供分页用户列表，支持按登录名、显示名称、状态和固定角色筛选；列表和详情仅返回公开用户字段及当前 `row_version`，不得返回密码或密码摘要。

#### Scenario: 查询包含多页的用户列表
- **GIVEN** 系统存在多个本地用户
- **WHEN** 管理员以有效的页码、页大小和筛选条件查询用户列表
- **THEN** 系统返回符合条件的当前页用户、总数和分页信息
- **AND** 每条用户仅包含 ID、登录名、显示名称、角色、状态、最近登录时间、版本号和必要的时间戳

#### Scenario: 查询结果为空
- **GIVEN** 没有用户符合管理员的筛选条件
- **WHEN** 管理员查询用户列表
- **THEN** 系统返回成功的空列表和零总数

### Requirement: 创建本地用户并分配固定角色
系统 SHALL 允许管理员创建具有唯一登录名、显示名称、密码和一个或多个固定角色的本地用户；固定角色元素 MUST 仅为 `admin`、`product_owner` 或 `reviewer`，新用户状态 MUST 为 `active`，密码 MUST 仅以摘要保存。

#### Scenario: 成功创建多角色用户
- **GIVEN** 管理员提供未使用的登录名、显示名称、密码及一个或多个允许的固定角色
- **WHEN** 管理员提交创建用户请求
- **THEN** 系统创建状态为 `active`、`row_version` 为 1 的用户并返回其公开信息
- **AND** 系统不在响应、审计详情或应用日志中暴露明文密码或密码摘要

#### Scenario: 登录名或角色无效
- **GIVEN** 管理员提供重复登录名、空角色集合或包含未允许角色的角色集合
- **WHEN** 管理员提交创建用户请求
- **THEN** 系统拒绝请求并返回稳定的字段级错误
- **AND** 系统不创建用户，也不写入 `audit_log`

### Requirement: 编辑用户资料和固定角色
系统 SHALL 允许管理员更新用户的显示名称和固定角色；更新请求 MUST 携带读取时获得的 `row_version`，并在成功更新后递增版本号。

#### Scenario: 使用当前版本编辑用户
- **GIVEN** 管理员持有用户当前的 `row_version`
- **WHEN** 管理员提交有效的显示名称和允许的非空固定角色集合
- **THEN** 系统保存更新并返回递增后的 `row_version`

#### Scenario: 并发编辑冲突
- **GIVEN** 另一位管理员已先更新同一用户，导致客户端持有过期的 `row_version`
- **WHEN** 管理员提交编辑请求
- **THEN** 系统返回稳定的并发冲突错误并要求刷新后重试
- **AND** 系统不得静默覆盖较新的显示名称、角色或状态，也不写入 `audit_log`

### Requirement: 管理员重置用户密码
系统 SHALL 允许管理员为指定用户重置密码；重置请求 MUST 携带当前 `row_version`，系统仅保存新密码摘要并在成功后递增版本号，不得暴露新旧明文密码。

#### Scenario: 成功重置密码
- **GIVEN** 管理员提供目标用户的当前 `row_version` 和有效的新密码
- **WHEN** 管理员提交重置密码请求
- **THEN** 系统更新该用户的密码摘要、递增 `row_version` 并返回更新后的公开用户信息
- **AND** 用户随后可使用新密码登录

#### Scenario: 过期版本重置密码
- **GIVEN** 管理员持有目标用户过期的 `row_version`
- **WHEN** 管理员提交重置密码请求
- **THEN** 系统返回并发冲突错误且不修改密码摘要
- **AND** 系统不写入 `audit_log`

### Requirement: 停用用户并保留历史
系统 SHALL 允许管理员停用用户而不物理删除记录；停用请求 MUST 携带当前 `row_version`，停用后用户的历史引用、角色和登录记录继续保留。

#### Scenario: 成功停用用户
- **GIVEN** 管理员持有活动用户当前的 `row_version`
- **WHEN** 管理员确认停用该用户
- **THEN** 系统将用户状态更新为 `disabled` 并递增 `row_version`
- **AND** 系统不删除该用户或其历史引用

#### Scenario: 停用已停用用户
- **GIVEN** 目标用户已经是 `disabled` 状态
- **WHEN** 管理员尝试再次停用该用户
- **THEN** 系统返回当前用户状态而不重复递增版本号
- **AND** 系统不新增审计记录

### Requirement: 用户管理变更审计
系统 MUST 将每次成功的用户创建、编辑、密码重置和停用，与对应 `app_user` 变更置于同一数据库事务中写入 `audit_log`；审计 MUST 记录操作者、时间、对象、对象 ID、动作及关键字段变化，且不得包含密码或密码摘要。

#### Scenario: 成功操作产生审计记录
- **GIVEN** 管理员执行成功的创建、编辑、密码重置或停用操作
- **WHEN** 用户变更事务提交
- **THEN** 系统同时提交一条对应的 `audit_log` 记录
- **AND** 密码重置的审计详情只标识密码已重置，不包含明文或摘要

#### Scenario: 失败操作不产生审计记录
- **GIVEN** 用户管理操作因验证错误、权限拒绝、并发冲突或事务失败而未提交
- **WHEN** 请求结束
- **THEN** 系统不新增与该操作相关的 `audit_log` 记录

### Requirement: 前端用户管理体验
前端 SHALL 在系统管理中提供仅管理员可用的用户列表和编辑交互，并 SHALL 显示加载、空、校验失败、服务错误及并发冲突状态；并发冲突时不得误导用户其修改已经保存。

#### Scenario: 管理员维护用户
- **GIVEN** 管理员进入系统管理用户页面
- **WHEN** 页面加载完成并执行创建、编辑、重置密码或停用操作
- **THEN** 前端提供固定角色多选、停用二次确认及操作成功后的列表/表单同步

#### Scenario: 前端呈现并发冲突
- **GIVEN** 用户编辑请求收到并发冲突错误
- **WHEN** 前端处理该错误
- **THEN** 前端保留未保存输入并明确提示用户刷新最新数据后重试
- **AND** 前端不得把该操作显示为成功

### Requirement: 当前浏览器退出登录
系统 SHALL 为已取得当前用户身份的访问者提供退出登录能力；退出请求 MUST 幂等清除当前浏览器的 `ots_user_id` Cookie，前端 MUST 清空内存中的身份状态并跳转登录页。退出 SHALL NOT 创建服务端会话、撤销记录或 `audit_log`。

#### Scenario: 已登录用户退出
- **GIVEN** 浏览器持有 `ots_user_id` Cookie 且前端已恢复当前用户
- **WHEN** 用户点击退出登录并且服务端处理 `POST /api/v1/auth/logout`
- **THEN** 服务端使用与登录时一致的 Cookie 名称和路径清除当前浏览器 Cookie
- **AND** 前端清空当前用户状态并跳转到登录页
- **AND** 用户可以立即使用另一个账号重新登录

#### Scenario: Cookie 已缺失或无效时退出
- **GIVEN** 浏览器未携带有效的 `ots_user_id` Cookie
- **WHEN** 访问者请求退出登录
- **THEN** 服务端仍返回成功并发送清除 Cookie 的响应
- **AND** 系统不查询或修改业务数据，也不写入 `audit_log`

### Requirement: 左侧三项应用导航
认证后的前端 SHALL 在桌面布局中使用左侧导航和右侧内容区；左侧主导航 MUST 严格按“工作台、用户与角色、运行状态”三个条目排列，并明确显示当前路由。小屏幕可以折叠导航，但条目名称和顺序不得改变。

#### Scenario: 管理员查看应用外壳
- **GIVEN** 当前用户已登录并具有 `admin` 角色
- **WHEN** 用户进入任一认证后页面
- **THEN** 左侧依次显示“工作台”“用户与角色”“运行状态”三个导航条目
- **AND** 当前页面对应条目具有文字、形状或位置之外的可感知选中状态

#### Scenario: 非管理员访问用户与角色
- **GIVEN** 当前用户已登录但不具有 `admin` 角色
- **WHEN** 用户通过左侧“用户与角色”条目进入对应路由
- **THEN** 前端展示明确的无权访问页面
- **AND** 服务端用户管理 API 仍执行管理员授权校验

### Requirement: 统一医疗科技主题
前端 SHALL 使用参考迈瑞医疗官方站点的红、白、深灰和冷灰医疗科技主题统一登录页、应用外壳、工作台、用户管理、运行状态和权限反馈；主题 MUST 保持正文与背景可读对比、清晰焦点状态和减少动效偏好支持，且不得复制第三方商标、图片或受保护页面素材。

#### Scenario: 桌面端主题一致
- **GIVEN** 用户在桌面视口访问登录页及认证后页面
- **WHEN** 页面完成渲染
- **THEN** 页面使用同一组主题变量、排版层级、边框、按钮和状态色
- **AND** 主操作使用品牌红强调，内容背景以白色和冷灰为主

#### Scenario: 键盘与减少动效用户访问
- **GIVEN** 用户使用键盘导航或启用 `prefers-reduced-motion`
- **WHEN** 用户操作导航、表单、按钮或弹窗
- **THEN** 所有可交互元素具有可见焦点
- **AND** 非必要进入和悬停动效被禁用或显著缩短
