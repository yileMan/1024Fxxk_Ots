## Context

参见 `proposal.md` 的动机。本 change 建立在已归档的 OTS-02/03/04 上：`app_user` 已保存固定角色，`product`、`product_version`、`ots_component` 和 `product_ots` 已可维护，当前产品、版本和 OTS 管理 API 统一使用管理员依赖。后续 OTS-06～23 会持续增加按产品版本限定的查询、评估、审核和导出接口，因此范围语义必须先形成一个可复用的服务端边界。

需求基线是《OTS 信息维护平台需求规格说明》V1.6 的 `FR-USER-003`、`FR-USER-004` 和权限规则 1～9；方案基线是《OTS 信息维护平台系统方案》V1.6 的固定角色、服务端范围校验和 `/scopes` 边界；数据基线是《OTS 信息维护平台数据表结构（11 表详细关系版）》V1.0 的第 2 张表 `user_product_scope`。本 change 只补齐该基线表，应用基础表总数仍为 11。

现有认证形式保持 ADR-04：后端从仅含用户 ID 的 `ots_user_id` Cookie 恢复用户，不新增签名、时效、令牌、请求来源或账号状态校验。范围授权不是认证机制，也不在浏览器存储授权明细或长期凭据。

## Goals / Non-Goals

**Goals:**

- 用一个数据模型表达产品级和版本级授权，并能稳定计算普通用户的有效产品版本并集。
- 将“已认证”“管理员”“有产品范围”“有版本范围”“具备业务角色/当前分配”拆成可组合的服务端校验。
- 让列表裁剪、详情拒绝、写操作、后续评估/审核和导出遵循同一范围语义，并保证分页总数不泄露范围外数据。
- 为管理员提供可验证的授权配置纵向切片，包含 API、页面、审计、错误和端到端测试。

**Non-Goals:**

- 不实现评估状态机、自审动作、审核动作、导入或评估导出；这里只定义后续动作组合授权校验的接口约束。
- 不开放产品、版本、OTS 主数据或产品 OTS 关联的写权限给普通用户；现有管理员管理页面和导航仍保持管理员专用。
- 不增加自定义角色、权限位、拒绝规则、组织层级、授权有效期或额外业务表。
- 不以本 change 改变用户停用或本地登录语义；现有认证与用户管理规范保持不变。

## Decisions

### 1. 严格采用基线 `user_product_scope` 表

新增编号迁移 `008_user_product_scope.sql`，字段、约束和索引遵循数据基线：

- `id`、`user_id`、`scope_type`、`product_id`、可空 `product_version_id`、`scope_key`、`created_by`、`created_at`、`updated_at`；
- `scope_type` 仅允许 `product`、`version`；`product` 范围要求版本为空，`version` 范围要求版本非空且服务端确认该版本属于 `product_id`；
- `scope_key` 由服务端规范化生成：产品级为 `product:<product_id>`，版本级为 `version:<product_version_id>`，客户端不得提交或覆盖；
- 唯一键为 `(user_id, scope_key)`，查询索引为 `(product_id, user_id)` 和 `(product_version_id, user_id)`；用户、授权人、产品和版本使用外键并禁止级联删除。

不在表中保存角色、状态、`row_version` 或展开后的版本集合。角色来自 `app_user.roles_json`，实体状态在计算时读取；若把版本集合物化到授权表，会在新建/停用产品版本时引入同步和失效风险。

备选方案是为每个有效版本都写一条版本授权，但这会丢失“整个产品”这一管理员意图，并使新增版本不能自动纳入产品级范围，因此不采用。

### 2. 使用细粒度幂等增删 API，避免整组覆盖并发

新增以下 OpenAPI 契约：

- `GET /api/v1/users/{user_id}/scopes`：管理员查询目标用户的显式授权及当前有效摘要；
- `POST /api/v1/users/{user_id}/scopes`：管理员授予一条范围，请求包含 `scope_type`、`product_id` 和可选 `product_version_id`；完全重复时返回现有记录且不新增审计；
- `DELETE /api/v1/users/{user_id}/scopes/{scope_id}`：管理员撤销一条属于目标用户的范围；已不存在时幂等返回且不新增审计；
- `GET /api/v1/scopes/me`：已认证用户查询前端所需的范围摘要，返回 `is_global`、显式授权和当前有效产品/版本 ID；管理员以 `is_global=true` 表示全局范围，不枚举全部 ID。

授予和撤销分别是单行事务，不提供“替换用户全部范围”的批量 `PUT`。基线表没有授权集合版本号，整组覆盖容易让两个管理员的页面互相静默覆盖；细粒度 API 配合唯一键可使重复授予幂等，并把并发影响限制在同一范围。未来确需批量编辑时，应另行增加显式并发令牌，而不是复用用户 `row_version`。

### 3. 显式授权和有效范围分开计算

显式授权保留管理员配置意图；有效范围用于请求判定：

1. 当前用户含 `admin` 角色时直接标记全局范围；
2. 普通用户的产品级授权展开为该产品当前全部 `active` 版本；
3. 版本级授权仅加入指定且所属产品与版本均为 `active` 的版本；
4. 多条范围取并集并去重；版本级授权与产品级授权可以重叠，撤销产品级授权后，重叠的显式版本授权仍然生效；
5. 停用产品或版本只使授权暂时无效，不删除显式授权，避免破坏历史和管理员配置意图。

范围解析通过 Repository 生成 SQL 子查询/谓词，不先读取全量 ID 再在内存过滤。产品列表按“产品级授权，或至少一个有效版本级授权”裁剪；版本和下游资源按版本谓词裁剪。分页 `items` 与 `total` 使用同一谓词，避免总数泄露。

### 4. 授权依赖分层组合，不让范围替代角色

后端提供四层可组合校验：

- 认证层：恢复当前用户；
- 平台角色层：`admin`、`product_owner`、`reviewer` 等固定角色；
- 范围层：管理员全局，或普通用户命中产品/版本有效范围；
- 业务资源层：后续评估接口再校验当前负责人、当前审核人、提交人和状态转换。

产品/版本的 GET 列表和详情改用认证层加范围层；POST/PUT/停用仍使用管理员依赖。授权版本的 OTS 清单 GET 使用版本范围依赖；OTS 主数据管理、关联增删、CSV 模板/导入/导出仍保持管理员依赖。详情或动作已确认资源存在但范围不匹配时返回 HTTP 403 和稳定错误码 `PRODUCT_SCOPE_FORBIDDEN`；资源本身不存在返回 404；未认证沿用现有 401。校验必须发生在序列化受保护数据和业务写入前。

后续 change 必须调用同一范围服务/查询谓词，再叠加自己的角色和资源条件；不得只根据前端按钮、请求参数中的用户 ID 或负责人字段做判断。管理员仅绕过范围层，不自动绕过负责人、审核人或禁止自审规则。

### 5. 授权变更使用现有事务审计模式

授予在插入 `user_product_scope` 后写 `audit_log(action=insert, object_type=user_product_scope)`；撤销在删除前捕获目标用户、范围类型、产品和版本，并写 `action=delete`。两者与业务变更使用同一 SQLAlchemy Session 事务提交。重复幂等、字段验证失败、403、404、唯一键竞态转为幂等结果时均不写审计；提交异常整体回滚。

审计详情不保存用户名快照、角色集合或任何认证 Cookie，只记录范围变更追溯所需 ID 和类型。授权查询和 `GET /scopes/me` 是只读操作，不写审计。

### 6. 前端配置显式范围，权限反馈由共享状态驱动

在现有用户管理页为管理员增加授权入口/区域，按产品分组显示产品级授权与版本级授权。产品级授权生效时，界面说明它覆盖当前全部有效版本；若同时存在显式版本授权，两条记录均显示，避免撤销产品级授权时意外丢失管理员原先配置。每次增删后重新读取目标用户授权，处理加载、空状态、字段错误、403、服务错误和重复幂等结果。

前端认证内存状态增加独立的当前范围摘要加载，不写入 `localStorage` 或 `sessionStorage`。路由 meta 和组件操作判断组合角色与范围；现有“产品管理”“OTS”“用户与角色”等管理员管理入口仍按原规范仅管理员可见。为直接输入无权路由及 API 403 统一导航/呈现现有 `ForbiddenPage`，404 继续使用 `NotFoundPage`。隐藏导航或按钮只改善体验，后端依赖始终执行最终校验。

OpenAPI 是请求/响应的唯一契约源；更新规范后重新生成 `front/src/api/generated.ts`，不手写重复类型。

### 7. 不新增业务状态机

授权只有“显式记录存在/不存在”和“因实体状态而有效/无效”两层，不引入授权状态字段。产品/版本从 `active` 变为 `disabled` 时，范围自然失效；恢复启用若未来被允许，原显式授权可重新生效。这样保持 11 表基线和最小状态空间。

## Risks / Trade-offs

- [产品级与版本级显式授权重叠，管理员可能误判撤销效果] → API 同时返回显式记录和有效摘要，界面明确显示覆盖来源；撤销后强制刷新有效摘要。
- [详情先区分存在再返回 403 会暴露 ID 是否存在] → V1 验收明确要求越权展示 403，响应只含稳定错误码和通用提示，不返回资源业务字段。
- [产品/版本停用后授权记录仍存在] → 运行时统一连接状态过滤；管理员界面将其标记为“当前无效”而非静默删除，保留历史意图。
- [未来接口绕过统一依赖] → 提供共享范围谓词与依赖，新增路由测试直接使用越权 ID；在 OTS-06～23 的 tasks/评审检查中复用该 capability。
- [唯一键并发授予触发数据库冲突] → 捕获唯一键竞态并重读现有范围，按幂等成功返回，不产生第二条审计。
- [管理员全局范围与业务动作权限混淆] → 代码和测试分别断言范围层与负责人/审核人层；管理员只绕过范围，不绕过业务动作条件。

## Migration Plan

1. 在空库和从当前 OTS-04 数据库升级两条路径执行 `008_user_product_scope.sql`，验证字段、CHECK/外键、唯一键、索引和迁移记录；迁移初始不写任何授权数据，因此普通用户默认没有产品范围，管理员仍全局可见。
2. 部署后端模型、Repository、Service、授权路由与范围依赖，再将产品/版本 GET 和授权版本 OTS 清单 GET 接入范围谓词；保持现有管理员写接口不变。
3. 生成 OpenAPI TypeScript 类型，部署授权配置 UI、当前范围状态和 403 反馈。
4. 执行角色/范围矩阵、MySQL 集成、前端组件和端到端测试，确认管理员原路径兼容、普通用户仅见授权范围、直接 API 越权被拒绝。

回滚时先回滚前端和后端到不引用 `user_product_scope` 的版本。数据库回滚说明必须要求先导出/备份授权和审计证据并确认允许丢弃本 change 的授权配置，再执行删除第 2 张表的回滚步骤；不得级联删除用户、产品、版本或 `audit_log`。若需要保留已配置授权，则只回滚应用，不执行数据库表删除。
