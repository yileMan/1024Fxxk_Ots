## Why

OTS-14 已能冻结提交快照并记录审核退回，但退回后当前记录保持只读，产品负责人无法基于退回意见形成新修订并重新提交；已完成结论也缺少受控的再次修订入口。OTS-15 需要补齐修订链、历史查询和版本对比，确保任何修改都不覆盖既有提交与审核留痕。

## What Changes

- 审核退回时保留被审核修订，复制其产品结论形成下一条当前 `returned` 修订，在同一事务内切换 `is_current`、建立 `parent_revision_id` 链并写入审计；原修订永久只读。
- 新修订继承产品分析、适用性、环境评分、影响、措施、依据和证据作为修改起点，清空提交与审核事件字段；退回意见通过父修订关联展示，不复制成新审核事件。
- 允许当前负责人编辑并重新提交当前 `returned` 修订；复用完整性、环境结果一致性、产品范围、当前人员分配、禁止自审和乐观锁校验，重新提交后进入 `submitted`。
- 为已完成当前修订提供显式“创建新修订”动作；新修订以 `reassess` 状态开放编辑，继承已完成业务快照、清空事件字段并要求记录修订原因，后续使用同一重新提交规则再次审核。自动来源变化创建修订仍由 OTS-16 实现。
- 提供同一产品 OTS/CVE 的修订历史和指定版本详情查询；历史按修订号稳定排序，始终受产品范围约束，非当前修订全部只读。
- 在评估详情增加修订时间线、退回/修订原因、历史版本查看和相邻版本字段级对比；页面始终明确当前版本与只读历史版本，并只按服务端动作能力开放编辑、创建修订和重新提交。
- 并发退回、创建修订或重新提交只能有一个请求成功；新旧当前切换、业务审计和审核动作在同一事务提交，失败不得留下多个当前修订、断裂链或部分审计。
- 不新增基础表或通知机制，不实现来源事实或候选依据变化的自动复评（OTS-16）、跨产品已审核参考（OTS-17）或全局追溯查询（OTS-19）。
- 覆盖 FR-REVIEW-004、FR-ASSESS-009 和产品评估状态/修订设计；依赖 OTS-14，并为 OTS-16 的自动待复评修订复用修订创建与重新提交机制。

## Capabilities

### New Capabilities

- `assessment-revision-and-resubmit`: 定义退回与已完成评估的新修订创建、单一当前修订、父子历史链、历史查询、版本对比及重新提交行为。

### Modified Capabilities

- `assessment-submit-and-review`: 将审核退回扩展为同事务保留被审核快照并创建下一当前修订，并允许退回或待复评新修订按完整校验重新提交。
- `assessment-editor-core`: 将可编辑边界扩展到 OTS-15 创建的当前 `returned`/`reassess` 修订，历史及原审核修订继续只读，并返回修订导航和动作能力。

## Impact

- 后端：评估退回、创建修订、重新提交、历史列表/详情/对比 API，请求响应 schema、服务与 repository 的修订复制、条件切换、授权、乐观锁和审计事务。
- 前端：评估详情页的修订时间线、退回与修订原因、历史版本只读查看、字段对比、当前修订编辑和重新提交交互，以及 OpenAPI 生成的 TypeScript 类型。
- 数据：复用 `product_assessment` 的 `revision_no`、`parent_revision_id`、`is_current`、状态、业务快照和提交/审核字段，复用 `audit_log`；预计无需新增表、字段或迁移。
- 测试与契约：新增后端单元/MySQL 并发与事务测试、OpenAPI 契约测试、前端组件测试及系统 Chrome Playwright 修订闭环冒烟测试。
