## Context

参见 `proposal.md` 的动机和 `assessment-editor-core` delta spec 的行为约束。OTS-10 已在既有 `product_assessment` 表中创建当前评估修订，OTS-11 已提供待办列表、漏洞详情和候选依据，但尚无按评估读取或写入草稿的服务。实现必须遵守《OTS-需求规格说明》V1.6、《OTS-系统方案》V1.6、《OTS-数据表结构（11 表）》V1.0，并保持应用基础表总数为 11。

现有 `product_assessment` 已包含本 change 所需的核心草稿字段、`owner_id`、状态、修订链、`row_version`、退回审核意见和 `reassess_reason`。现有身份恢复、有效产品范围、漏洞目录查询和审计模型可复用；本次不需要迁移。评估详情跨越产品、版本、产品 OTS、OTS、漏洞和候选匹配，更新则必须把授权复核、条件校验、乐观锁和审计置于同一事务边界。

## Goals / Non-Goals

**Goals:**

- 提供一个按评估 ID 聚合的详情契约，供同一 Vue 页面展示事实、候选和当前产品草稿。
- 以单条条件更新保证只有当前负责人能够修改当前可编辑修订，且并发写入不会静默覆盖。
- 允许负责人增量保存未完成草稿，同时对已经选择的结论执行必要的条件校验。
- 复用现有 11 张表和 OpenAPI 生成链，提供可独立测试的后端、前端和纵向验收路径。

**Non-Goals:**

- 不实现自动保存队列、离线草稿、本地持久化或多人协同编辑。
- 不实现 CVSS 环境指标、分数或向量的编辑与计算；详情只读展示 OTS-11 已有来源 CVSS。
- 不实现提交、通过、退回、修订创建或任何评估状态转换。
- 不展示其他产品评估，不增加附件上传；`evidence_text` 仅保存文字说明或内网引用位置。

## Decisions

### 1. 使用评估资源详情和独立草稿子资源

新增以下契约：

- `GET /api/v1/assessments/{assessment_id}`：返回评估上下文、当前产品草稿、可编辑标志、原因提示，以及复用 OTS-11 语义的来源事实和范围内候选依据。
- `PUT /api/v1/assessments/{assessment_id}/draft`：接收完整核心草稿字段与必填 `row_version`，返回更新后的同一详情响应。

采用 `PUT` 是因为页面使用明确保存并提交完整表单快照，便于统一做跨字段条件校验和无变化比较。替代方案是通用 `PATCH /assessments/{id}`，但它容易与 OTS-14 的状态字段混合，也会使部分更新的缺失值和清空语义复杂化。状态变化仍保留给后续显式 `/submit` 等动作接口。

API 对不存在返回 `404`，对存在但超出有效产品范围返回 `403`；可见但不可编辑的更新返回 `409 ASSESSMENT_NOT_EDITABLE`，旧 `row_version` 返回 `409 ASSESSMENT_VERSION_CONFLICT`，字段问题返回包含路径的 `422 ASSESSMENT_VALIDATION_ERROR`。响应不暴露未授权关联或其他产品草稿。

### 2. 详情查询复用授权范围并返回服务端可编辑判定

repository 以评估为根连接 `product_ots → product_version → product`、`ots_component` 和 `vulnerability`，再用 `(ots_component_id, vulnerability_id)` 读取唯一候选匹配。service 先区分资源不存在和不可见，然后按“当前修订 + 可编辑状态 + 当前 `owner_id` + 有效产品范围”计算 `editable`，前端不自行推断授权。

管理员仍可按 OTS-11 的全局只读规则读取，审核人和其他有范围用户可读取其范围内详情，但只有 `owner_id` 匹配者可编辑。此选择把角色导航和真正授权分离，防止管理员角色被误用为代写权限。替代方案是把详情拆成多次现有 API 请求，会产生跨请求状态漂移并让前端负责拼接权限语义，因此不采用。

历史修订读取不是本次新增导航入口，但查询层不把 `is_current=0` 误判为不存在；有权用户读取时返回只读。这样为后续修订历史复用契约，同时不在本 change 建设历史列表。

### 3. 草稿校验分为字段合法性、条件合法性和提交完整性

Pydantic schema 负责枚举、类型和文本上限；service 将所有可空文本去除首尾空白并把空串规范化为 `null`，随后执行跨字段规则：

- `applicability=pending` 允许无依据；选择其他适用性时 `applicability_basis` 必填。
- `treatment` 允许为空，以支持增量草稿；选择 `accept_risk` 或 `no_action` 时 `treatment_detail` 必填。
- 核心长文本采用契约中统一的有限上限，`evidence_text` 只作为纯文本或内网引用位置，不解析 HTML、URL 或文件路径，也不读取引用目标。

分析摘要、触发条件、涉及功能、产品影响、现有控制、处置和必要证据在最终提交前必须完整，但完整性门属于 OTS-14 的 `/submit`；本 change 的草稿保存不能因未完成字段而失败。替代方案是在每次保存时套用提交校验，会使负责人无法逐步填写，与草稿语义冲突。

处置枚举在 API 层固定为 `patch_or_upgrade`、`configuration_mitigation`、`isolation_or_compensating_control`、`accept_risk`、`no_action`、`further_investigation`。现有数据库字段为可空字符串且没有处置检查约束，因此无需迁移；后续所有写入口必须复用同一枚举定义。

### 4. 使用带全部可编辑谓词的原子条件更新

保存事务先读取可见上下文和规范化旧值，用于权限诊断、无变化判定与审计摘要；有实际变化时执行单条条件更新，其谓词同时包含：

- `id=assessment_id`；
- `is_current=1`；
- `status IN ('pending','returned','reassess')`；
- `owner_id=current_user.id`；
- `row_version=request.row_version`。

有效产品范围在同一事务保存前重新验证。更新成功时同时写入字段、`updated_at` 并令 `row_version=row_version+1`。若受影响行数为零，service 重新读取最小状态来区分版本冲突、状态/当前修订冲突和权限变化，但不会回显其他用户草稿。MySQL 默认事务隔离与条件更新足以阻止丢失更新，不引入显式长事务页面锁。

无变化请求在已完成权限和版本检查后直接返回当前详情，不更新 `updated_at`、版本或审计。替代方案是所有保存都递增版本，实现更简单，但会制造虚假变更、无意义审计和额外冲突。

### 5. 审计记录变更字段而不复制敏感长文本

实际更新成功后，在同一 SQLAlchemy session 和事务添加 `AuditLog(action='update', object_type='product_assessment', object_id=<id>)`。`detail_json` 包含 `revision_no`、`changed_fields`、`row_version` 前后值；适用性和处置枚举可记录前后值，长文本只记录是否为空、字符数和内容 SHA-256，不保存正文。这样既能证明哪些字段何时变化，又避免把内部证据复制到审计表。

不新增“填写人”字段；操作者只存在于每次审计记录，`owner_id` 继续表示当前责任人。事务由 service 统一提交；任何异常回滚评估更新和审计。替代方案是为每个按键或字段写审计，会产生大量记录且无法表示一次明确保存的原子意图。

### 6. 前端采用单页完整表单和显式并发恢复

新增 `/system/assessments/:assessmentId` 路由与评估详情页。OTS-11 待办列表的评估项进入该路由；漏洞详情仅在有明确可见评估 ID 时提供入口。页面顺序遵循系统方案：顶部原因提示、来源信息、候选匹配、当前产品结论；未纳入本 change 的跨产品参考、环境评分编辑和审核动作不显示占位控件。

表单保留服务端返回的 `row_version`，保存时发送完整规范化前的用户输入。成功后完全用响应重置表单与基线；`422` 映射到字段，其他错误保留未保存输入。并发 `409` 不自动重放请求，也不自动以服务器值覆盖本地表单；页面提示用户刷新，并在确认刷新前保留当前输入。状态不可编辑冲突则禁用继续保存并提供重新加载。

不采用自动保存，因为它会增加并发时序、节流、离开页面和审计噪声处理，本 change 以明确保存满足任务要求且更容易验收。

### 7. 分层测试锁定权限、原子性和界面状态

后端先以失败测试覆盖详情范围、当前负责人、全部草稿状态、条件校验、无变化保存、并发双方、范围撤销和事务回滚。MySQL 集成测试使用两个独立 session 验证条件更新，并确认审计与业务行原子提交。API 测试锁定响应 DTO、处置枚举及 `403/404/409/422` 错误码和字段路径。

前端组件测试覆盖加载、原因、可编辑/只读、字段错误、保存状态和冲突时本地输入保留；Playwright 按项目规则使用系统 Chrome 覆盖负责人从待办进入、保存、第二客户端冲突及非负责人只读。OpenAPI 重复生成必须一致，新增代码覆盖率不低于 80%。

## Risks / Trade-offs

- [详情聚合复用 OTS-11 数据时出现响应语义漂移] → 抽取或复用同一来源事实/候选 DTO 与映射测试，不在前端重新解释候选结论。
- [读取后人员、范围或状态发生变化造成越权写入] → 每次保存都在后端重新验证范围，并把负责人、状态、当前修订和版本放入原子更新条件。
- [条件更新失败原因二次读取时状态再次变化] → 错误分类只用于用户提示，任何零行更新都视为未保存；客户端必须刷新，不依据错误详情继续写入。
- [长文本审计摘要不足以直接还原正文] → 评估当前值和后续修订承担业务内容保存，审计用字段名、长度和哈希证明变化；完整历史查询留给 OTS-19。
- [草稿允许不完整数据可能被误认为可提交] → 页面明确标记草稿，保存不改变状态；OTS-14 在提交动作中执行完整性门。
- [处置枚举仅由应用约束，直接数据库写入可能绕过] → 所有产品评估写操作集中复用 schema/service 枚举；V1 不为此新增迁移，集成测试覆盖持久化值。

## Migration Plan

1. 不执行数据库迁移；先增加后端 schema、repository、service 和评估详情/草稿路由，运行单元、API 与 MySQL 并发/事务测试。
2. 重新生成并提交 OpenAPI JSON 和 TypeScript 类型，验证连续两次生成无漂移。
3. 增加评估详情路由、页面、薄 API client 和待办入口，运行 Vitest、类型检查和生产构建。
4. 使用系统 Chrome 运行负责人保存、并发冲突和非负责人只读的 Playwright 流程，再完成需求追溯与 OpenSpec 严格校验。

回滚只需回退本 change 的后端、生成契约和前端代码；既有草稿字段及审计表不变。已通过新接口保存的草稿保持有效，旧版本应用只是无法继续通过界面编辑，无需数据回滚。
