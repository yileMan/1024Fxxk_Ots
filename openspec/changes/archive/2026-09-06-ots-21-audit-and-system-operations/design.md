## Context

参见 `proposal.md` 的 Why。当前 `audit_log` 已由迁移创建，用户、授权、产品、OTS、导入匹配和评估流程分别在 service 内直接构造审计记录；这些记录与业务写入大多共用事务，但详情形状和覆盖证明分散，系统也没有审计查询 API。现有 `GET /api/v1/health` 只提供基础存活检查；`import_batch` 可提供最近导入/失败事实，而 OTS-22 尚未交付备份脚本及其运行产物。

本设计以需求规格 V1.6 的 FR-AUDIT-001～003、关键验收规则 19、系统方案 V1.6 的 11.3，以及数据结构 V1.0 的 `audit_log` 定义为基线。V1 必须继续限定为 11 张应用基础表、单体应用和单节点 MySQL，不为运维状态、告警或审计查询增加业务表。

## Goals / Non-Goals

**Goals:**

- 以一个小型统一审计构造器固定动作、对象、差异和脱敏规则，同时保持审计写入由调用方当前事务负责。
- 证明所有既有核心写路径的成功、回滚、幂等和批量边界，而不是只覆盖 OTS-21 新增端点。
- 提供可利用现有索引稳定分页的管理员审计查询，并安全渲染异构历史 `detail_json`。
- 将运行状态建模为相互独立的有界探测，局部失败时仍返回其他诊断。
- 先定义 OTS-22 可写入的最小备份状态文件契约；OTS-21 只消费它且兼容尚未配置的环境。

**Non-Goals:**

- 不把 SQLAlchemy 事件、数据库触发器或 binlog 当作 V1 审计源，也不追踪绕过应用直接执行的 DBA SQL。
- 不补录历史缺失审计，不修改已有记录，不提供审计导出、清理、保留期调度或防篡改哈希链。
- 不执行备份/恢复、不检查备份内容可恢复性、不实现告警通知或独立监控代理。
- 不增加认证能力，也不在公开健康检查中暴露管理员诊断。

## Decisions

### 1. 使用显式统一审计构造器，不使用 ORM 全局事件或数据库触发器

新增集中式审计帮助模块，接收当前 `Session`、操作者、限定动作、对象类型/ID 和已脱敏详情，只执行 `session.add(AuditLog(...))`，不自行 `commit`。业务 service 在确认实际变化后调用它，最终仍由原事务一次提交；异常路径由现有事务边界整体回滚。

统一模块定义详情版本和稳定形状：单条更新使用 `{"schema_version": "1.0", "changes": {field: {"from": ..., "to": ...}}}`，新增/删除使用受控 `values`/`reason`，批量写入使用 `batch_no` 与分类计数。详情采用字段白名单和长度上限，密码相关字段只记录布尔事件标记，长文本只记录“已变化”及必要摘要哈希，不保存正文。

数据库触发器无法可靠取得应用用户和业务批次语义；ORM 全局事件容易把内部状态维护、回滚前 flush 或只读加载误记为业务动作。显式调用虽然需要逐路径复核，但最符合 FR-AUDIT 的业务边界，也能保持现有最小架构。

### 2. 先建立写路径清单，再做最小集中化

实施时以 10 张非审计基础表的所有 API/后台写入口为清单，逐项标明 `insert/update/delete/batch_upsert`、操作者来源、事务边界、幂等行为和详情字段。现有满足契约的写入只替换为统一构造器，不重构业务 service；发现缺失才补充审计及失败测试。

“核心业务数据”解释为应用 10 张非审计基础表中经业务 service 或导入/匹配后台任务产生的持久化变化；迁移元数据、应用日志、文件状态和审计表自身不递归审计。一个业务操作可产生多种对象变化，但批量导入必须按批次聚合，不能因逐行 ORM 操作制造海量记录。

### 3. 审计查询采用管理员专用列表和详情端点

新增：

- `GET /api/v1/audit-logs`：接受 `object_type`、`user_id`、`action`、`created_from`、`created_to`、`cursor`、`limit`；返回结果、总数和下一游标。
- `GET /api/v1/audit-logs/{audit_log_id}`：返回单条完整脱敏详情。

两个端点均先校验登录和管理员角色，使用只读 session，且不写访问审计。列表按 `created_at DESC, id DESC` 排序，游标编码这两个值；总数按同一过滤条件单独计算。时间输入使用带时区 ISO 8601，在 API 边界归一化为项目约定时区后查询 `DATETIME(3)`；起止时间均包含边界。

`object_type` 使用当前服务支持的白名单，动作使用数据库四值枚举，用户筛选只接受正整数。列表返回详情摘要而非完整大 JSON，详情端点再返回结构化差异。历史详情若不符合新版本形状，前端以只读键值树安全降级，不修改历史数据。

offset 分页实现简单，但十年保留会使深页查询变慢且并发新增时漂移，因此采用 keyset。全文检索、任意 JSON 字段查询和审计导出不属于本 change。

### 4. 保持既有 `audit_log` 表和索引，性能证据不足时不迁移

查询条件优先匹配现有 `idx_audit_time(created_at)`、`idx_audit_user_time(user_id, created_at)` 和 `idx_audit_object(object_type, object_id, created_at)`。动作过滤可能在时间范围内二次筛选；先以真实 MySQL、十年规模代表性数据和组合条件执行计划验证。只有 P95 或扫描量证明确有问题时，才提出最小前向索引迁移并提供回滚说明；不得增加第 12 张表或额外迁移框架表。

### 5. 运行信息使用分项探测器和确定性聚合

新增管理员端点 `GET /api/v1/system/operations`，一次响应包含 `application`、`database`、`disk`、`backup`、`latest_import`、`latest_failure` 六个分项以及 `overall_status`、`observed_at`。每个分项统一为 `status`、`observed_at`、`summary` 和受控数据字段；状态严重度为 `error > warning > unknown > ok`，整体取最高严重度。

- 应用：从构建时注入的版本和可选提交标识读取；缺失则 `unknown`，不运行 Git 命令。
- 数据库：使用当前连接池执行有超时的轻量 `SELECT 1`；只返回可用性与探测耗时，不返回 DSN、版本横幅或 SQL 错误。
- 磁盘：只对配置的持久化根目录调用单文件系统容量 API，返回总量、可用量、使用比例和阈值状态；不递归扫描目录。
- 导入：从 `import_batch` 分别查询最新批次和最新失败批次，返回批次号、状态、起止时间及受控计数，不返回文件绝对路径、错误正文或 manifest。
- 备份：读取配置项 `backup_status_file` 指向的状态文件，见下一决策。

各探测器独立捕获异常并使用短超时。身份校验仍依赖数据库：若请求开始时数据库已完全不可用，详细端点可能在认证阶段返回统一服务错误；公开健康检查用于外部发现此故障。若认证后某次数据库探测失败，则详细响应按分项降级返回。

### 6. 备份状态通过受限原子 JSON 文件与 OTS-22 解耦

OTS-21 定义并只读消费 `backup-status-v1.json`：包含固定 `schema_version`、`status`（`success`/`failed`）、`started_at`、`finished_at`、相对 `file_name`、`size_bytes` 和可选安全错误码。文件必须位于配置的备份状态目录内，使用 UTF-8、固定大小上限、拒绝符号链接逃逸和路径分隔符；响应只展示安全文件名，不返回绝对路径或错误正文。

OTS-22 的备份脚本以后以“临时文件写入 + 同目录原子替换”更新该文件。未配置、不存在分别映射为 `unknown`；格式错误、未知版本或陈旧的 `running` 状态映射为 `error`/`warning`。OTS-21 不创建状态文件、不列举备份目录，也不根据文件名猜测成功。

把备份执行记录写入数据库会要求新表或挪用 `import_batch`，均违反 11 表语义；扫描目录只能证明文件存在，不能证明备份结果。因此选择显式、可版本化的文件契约。

### 7. 前端分为同一系统管理域下的两个页面

“变更记录”页使用服务端筛选与分页，筛选变化清空旧游标；抽屉/对话框展示结构化差异，JSON 键和值均按文本渲染。时间筛选显示当前时区，空结果、无操作者的系统任务、未知历史详情格式分别有明确状态。

“运行状态”页按卡片展示整体及六个分项，进入页面和用户主动刷新时请求，不做高频轮询；保留上次成功观测时间，但新请求失败时明确标为陈旧，不能把旧状态继续显示为正常。前端隐藏非管理员导航仅用于体验，后端角色校验始终是安全边界。

合并成一个超大页面会混淆长期审计检索与瞬时状态观测；拆成两个路由但保持同一系统管理导航域，既符合任务描述也便于独立处理加载和错误。

### 8. 公开健康检查维持最小契约

保留 `GET /api/v1/health` 作为进程存活探测，不加入数据库、磁盘、备份或导入详情。详细状态只由管理员端点返回。应用结构化日志可记录探测类型、结果、耗时和非敏感错误码，但不得写 Cookie、连接串、文件正文或绝对路径，也不得进入 `audit_log`。

## Risks / Trade-offs

- [显式审计容易遗漏新增写路径] → 建立写路径矩阵和自动化契约测试，并在代码评审中把同事务审计作为新增写 service 的检查项。
- [集中详情格式与历史记录不一致] → 不迁移或重写历史 JSON，API 标记 schema 版本，前端提供安全降级展示。
- [十年审计量使组合筛选变慢] → 使用 keyset、有界时间/页大小、真实 MySQL 执行计划和代表性规模压测；只依据证据决定最小索引。
- [审计详情可能间接泄露敏感业务内容] → 使用字段白名单、长度限制和类型化脱敏，长文本仅保留变化标记或摘要哈希，并增加恶意 JSON/HTML 测试。
- [备份状态文件可陈旧或被部分写入] → 使用 schema、时间合理性、大小和路径校验；要求 OTS-22 原子替换，无法验证时显示未知/故障而非成功。
- [数据库故障导致管理员身份无法校验] → 公开健康检查负责暴露应用不可用信号；详细端点绝不为绕过认证而公开内部诊断。
- [运行探测拖慢请求或放大故障] → 使用轻量操作、逐项短超时、不递归扫描，并让局部失败快速降级。
- [应用仅能看到经业务层发生的变更] → 明确 V1 审计边界；DBA 直连活动由组织数据库审计或后续能力处理，不在本 change 假装覆盖。

## Migration Plan

1. 先增加审计写路径矩阵、回滚/幂等/脱敏失败测试和运行状态权限/故障测试，不改变数据库。
2. 引入统一审计构造器并逐个迁移现有调用点；每次保持业务事务边界不变，确认旧记录仍可读取。
3. 实现审计列表/详情和运行信息 API，生成 OpenAPI 与 TypeScript 类型并检查连续生成无漂移。
4. 实现两个系统管理页面及组件测试，再用系统 Chrome 验证查询、差异查看、权限和故障显示。
5. 在真实 MySQL 8 上验证成功/回滚原子性、组合查询执行计划、代表性十年数据规模和 10～20 并发 P95；若无需索引则不创建迁移。
6. 发布时先后端后前端。回滚时先回滚前端再回滚后端；统一构造器产生的 `detail_json` 保持向后可读，不删除已产生审计。若本 change 最终新增索引，只按独立回滚说明删除该索引，绝不删除 `audit_log` 或业务数据。
