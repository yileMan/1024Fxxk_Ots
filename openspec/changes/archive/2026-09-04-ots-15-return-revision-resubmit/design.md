## Context

参见 `proposal.md` 的动机和范围。OTS-14 已提供 `/submit`、`/approve`、`/return` 动作、基于状态与 `row_version` 的条件更新、提交完整性门、当前人员分配与产品范围校验，以及同事务 `audit_log`；当前 `/return` 只把原行标为 `returned`，尚不创建下一修订。现有评估详情按 ID 读取记录，但前端主入口主要面向当前修订。

需求基线是 `doc/OTS-需求规格说明-V1.6.md` 的 FR-REVIEW-004 与 FR-ASSESS-009，方案基线是 5.3 状态机、9 章动作接口和 13.2 退回重提集成验收；数据基线是 `doc/OTS-数据表结构-11表-V1.0.md` 第 10 张表及关键事务规则 7。`product_assessment` 已有 `revision_no`、`parent_revision_id`、`is_current`、完整业务快照和提交审核字段，V1 的 11 张基础表无需扩展。

## Goals / Non-Goals

**Goals:**

- 建立一个可由退回、人工修改完成记录和后续 OTS-16 自动复评共同复用的修订创建原语。
- 以数据库事务和条件写入保证修订号连续、父子链完整及单一当前修订。
- 保持每条已提交或已审核修订不可变，同时让后续修订继承业务快照、清空事件字段并可重新提交。
- 在同一评估详情页面支持当前编辑、历史时间线、指定版本只读查看与字段级对比。

**Non-Goals:**

- 不检测漏洞、候选匹配、CVSS、KEV 或产品上下文变化，也不自动创建待复评修订；这些由 OTS-16 触发。
- 不提供跨产品已审核参考、全局 CVE 追溯或导出；分别由 OTS-17、OTS-19 和 OTS-20 完成。
- 不新增修订表、事件表、通知表、消息队列或数据库字段，不允许编辑或删除历史修订。

## Decisions

### 1. 退回事务同时完成审核留痕和下一修订创建

扩展现有 `POST /api/v1/assessments/{assessment_id}/return`：在锁定并验证当前 `submitted` 行后，先把原行写成含完整审核留痕的 `returned` 非当前修订，再插入下一条 `status=returned` 当前修订。两条行更新、插入及审计使用同一事务；响应返回新当前详情并携带原退回修订摘要。

新行复制所有产品分析、结构化环境指标和服务端派生结果，以及当时的来源基准和责任人；清空提交与审核事件字段，`row_version` 从 1 开始。退回意见只保存在父修订，由详情按 `parent_revision_id` 读取，避免同一审核事件在两条记录上出现。替代方案是在原 `returned` 行上直接编辑，会覆盖已审核快照；先提交退回再另事务创建修订则会暴露没有可编辑当前记录的中间状态。

### 2. 人工修改完成记录使用显式创建修订动作

新增 `POST /api/v1/assessments/{assessment_id}/revisions`，请求仅含 `row_version` 和必填 `revision_reason`，额外字段禁止。动作只接受当前 `completed` 修订，并重新校验 `product_owner` 固定角色、有效产品范围、产品版本当前指定负责人和当前修订 `owner_id`；成功后生成 `status=reassess` 的当前修订。

选择 `reassess` 是因为数据基线没有独立“修订中”状态，且现有工作台已经把该状态分配给负责人；人工修订原因复用现有 `reassess_reason` 字段，并由响应中的稳定原因类型区分人工修订与 OTS-16 后续自动触发。替代方案使用 `pending` 会把已审核结论的再次修订混入首次评估待办，丢失流程语义。

### 3. repository 提供统一的锁定与克隆原语

服务在事务内按业务键读取当前行并加锁，以数据库中的 `MAX(revision_no)+1` 生成下一修订号；随后以评估 ID、业务键、`is_current=1`、预期状态和 `row_version` 条件将父行降为非当前，再插入子行。唯一修订键防止重复号，服务级当前行锁和条件更新保证同一业务键的并发请求仅一个成功。

统一克隆字段白名单，明确“复制业务快照、清空事件字段、重置系统字段”，供退回、人工修订和 OTS-16 后续调用；调用方只决定触发状态和原因类型。替代方案让各服务自行复制 ORM 对象，容易遗漏新业务字段或误复制主键、审核留痕和行版本。

### 4. 重新提交复用现有 submit 而不新增 resubmit 接口

现有 `POST /api/v1/assessments/{assessment_id}/submit` 扩展接受当前 `pending`、`returned` 或 `reassess`，其余授权、最终完整性、环境重算、当前审核人非本人、条件更新和审计规则保持一致。审计 detail 区分 `submit` 与 `resubmit`，但外部动作契约保持单一。

后续修订只写本行的 `submitted_by/submitted_at`，父修订事件不变。替代方案新增 `/resubmit` 会复制完整校验和前端错误处理，且两者仅来源状态不同。

### 5. 历史 API 围绕业务链而非任意全局查询

增加 `GET /api/v1/assessments/{assessment_id}/revisions` 返回同一 `(product_ots_id, vulnerability_id)` 的修订摘要，按 `revision_no DESC, id DESC` 排序；既有详情读取保留指定 ID 语义，并增加父修订、当前标记、原因和动作能力。比较使用窄接口 `GET /api/v1/assessments/{assessment_id}/revision-comparison?base_revision_id=&target_revision_id=`，服务端确认两 ID 属于同一链后返回字段白名单差异。

所有读取复用有效产品范围检查；历史响应中的动作能力恒为 false，当前入口成功写入后以前端响应中的新评估 ID 替换路由。替代方案一次返回所有修订完整正文会放大响应、授权和前端状态复杂度；全局历史检索则越过 OTS-19 边界。

### 6. 前端用单页双层状态区分“路由版本”和“服务器当前版本”

评估详情顶部增加修订时间线与当前标记。用户选择历史版本时按其 ID 重新取详情并锁定所有表单；页面同时保留服务端返回的当前修订入口，允许一键返回当前版本。默认比较历史版本与父版本，也允许在同链中选择两个版本；差异值全部按纯文本呈现。

退回成功后审核人的页面跳转到响应返回的新当前修订并显示退回意见；负责人进入 `returned` 当前修订后编辑和重新提交。`403` 表示范围或人员分配变化，`409` 提示刷新当前链，`422` 映射原因或结论字段，其他失败保留未提交输入。前端按钮只使用服务端动作能力，不能从状态自行放行。

### 7. 审计记录触发动作与链关系，不复制正文

一次退回事务写一条涵盖审核决定与父子修订切换的业务审计，避免将原行更新和子行插入误呈现为互不相关事件；人工创建修订另写一条审计。detail 记录触发动作、业务键、父/子 ID 与修订号、状态/当前标记和操作者，不包含完整退回意见、修订原因、证据或产品结论。重新提交继续使用 OTS-14 的状态转换审计。

## Risks / Trade-offs

- [MySQL 仅有修订唯一键，没有“单一 current”部分唯一索引] → 对业务键当前行加锁、使用带预期状态和行版本的条件更新，并以双会话集成测试验证竞争请求；所有入口统一走同一修订原语。
- [退回接口成功响应从原修订变为新当前修订，旧前端可能继续展示错误 ID] → OpenAPI 明确返回 `current_revision` 与 `reviewed_revision` 摘要，前端在同一 change 更新并增加契约回归测试。
- [复制字段白名单未来可能遗漏新增业务字段] → 白名单集中定义，并用完整模型字段集合测试要求每个非系统字段明确归为复制、清空或重算。
- [人工 `reassess` 与 OTS-16 自动复评共享状态，原因语义可能混淆] → 响应和审计携带稳定原因类型，OTS-16 复用相同创建原语但提供自动触发类型和变化摘要。
- [历史版本包含证据和退回意见] → 严格复用当前产品范围，不提供跨产品访问；前端按不可信纯文本渲染，比较接口使用字段白名单。
- [长修订链导致详情一次加载过大] → 时间线接口只返回摘要并采用稳定分页或 V1 有界返回策略；正文与差异按需加载，不预取全部完整修订。

## Migration Plan

1. 先增加后端失败测试与 OpenAPI 契约，再实现统一修订原语、退回事务、人工创建修订、历史/比较读取及重新提交状态扩展。
2. 更新生成的 TypeScript 类型和评估详情页，增加修订时间线、历史只读、差异及退回/人工修订交互；使用系统 Chrome 完成退回到重提再审核的端到端验证。
3. 本 change 预计无需数据库迁移；部署前检查现有数据是否存在多个 current、断裂父链或重复修订号。异常数据只报告并通过单独审批的数据修复处理，不在应用启动时自动改写。
4. 回滚应用代码时，新创建的修订仍是有效业务历史，不删除、不合并也不恢复旧 current。若旧版本无法处理退回即创建子修订的语义，应回滚前停止相关写操作并保持新版本后端直到兼容版本部署。
