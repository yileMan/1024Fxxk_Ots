## Context

当前系统已通过 OTS-02 提供本地用户、固定角色、管理员授权和审计能力，但尚无产品与产品版本业务表、API 或界面。实现必须遵循 `doc/OTS-数据表结构-11表-V1.0.md` 的 11 表基线，复用现有 FastAPI 分层、SQLAlchemy、编号 SQL 迁移、OpenAPI 生成类型以及 Vue 管理端模式。动机见 [proposal.md](proposal.md)，行为见 `specs/product-version-management/spec.md`。

## Goals / Non-Goals

**Goals:**

- 交付 `product`、`product_version` 的完整管理员纵向切片，并与现有用户角色和审计机制一致。
- 在数据库和服务层同时约束唯一性、人员资格、状态、乐观锁与不可物理删除。
- 为 OTS-04 的产品 OTS 关联及后续授权、评估流程提供稳定主数据与当前分配字段。

**Non-Goals:**

- 不创建 `product_ots` 或任何 OTS 主数据、CSV 导入导出能力；这些属于 OTS-04。
- 不创建授权或产品评估任务表，也不在本变更中转交任务；当前人员调整规则以未来下游记录不被改写的契约实现。
- 不改变现有固定角色、认证机制、外网数据边界或 11 表外的数据模型。
- 不改变既有认证、固定角色、外网数据边界或 11 表外的数据模型；左侧导航的扩展仅限新增“产品管理”管理员入口。

## Decisions

### 以两张基线表承载产品与版本

新增编号 SQL 迁移创建 `product` 和 `product_version`，使用基线规定的列、外键、唯一键及索引；`product_code` 全局唯一，`(product_id, version_no)` 产品内唯一，状态仅为 `active` 或 `disabled`，并使用 `row_version` 乐观锁。

选择该方案是为了与既定 11 表模型和后续外键保持一致。替代方案是将版本嵌入产品 JSON 或另建简化表；两者都会破坏基线关系、查询约束和后续 `product_ots` 引用，因此不采用。

### 在服务层验证人员资格，在数据库保留引用完整性

版本创建、编辑和停用经服务层执行：读取负责人和审核人用户，验证其状态及固定角色，使用预期 `row_version` 条件更新，并在同一事务写入审计。数据库外键保证人员和产品引用存在，唯一键防止并发下的重复。

选择服务层资格验证是因为固定角色位于用户角色关联数据中，不能以单列表级检查可靠表达。仅依赖前端筛选会被直接 API 调用绕过；仅靠数据库触发器会增加不在现有架构内的隐式业务逻辑，均不采用。

### 统一 API 与错误契约

在 `/api/v1/products` 及其版本子资源提供分页查询、详情、创建、更新和停用；请求和响应均携带 `row_version`。路由复用 OTS-02 的管理员依赖与错误详情结构，区分未找到、唯一键冲突、人员资格校验和乐观锁冲突，并在成功状态变更后返回最新公开字段。

选择资源化 API 与用户管理端点保持一致，便于 OpenAPI 生成前端类型。替代方案是单个“保存建档向导”复合端点；它会把独立版本维护与错误定位耦合，因此不采用。

### 前端以顶级导航和可恢复表单完成管理流程

前端在认证后左侧导航新增仅管理员可见的“产品管理”顶级入口，并在该路由提供产品列表、筛选、分页、创建、编辑、停用与版本展开/进入维护；建档向导前两步先保存产品基本信息，再创建首个版本。负责人和审核人下拉项由后端受限查询或现有用户接口的角色/状态筛选提供，服务端仍为最终校验。冲突时保留本地输入并提示重新读取。

修改既有应用外壳规范，将左侧主导航扩展为“工作台、产品管理、用户与角色、运行状态”，并保持“产品管理”和“用户与角色”均仅管理员可访问。替代方案是把入口放在工作台；这会降低主数据管理的可发现性，因此不采用。

## Risks / Trade-offs

- [OTS-04 之前没有产品 OTS 或评估任务可转交] → 本变更验证当前分配和历史不可改写契约；实际待办转交在创建 `product_assessment` 后由相应变更实现并回归测试。
- [用户角色在版本保存后被管理员调整或用户被停用] → 保存及后续每次重新分配均校验资格；不回写既有版本历史，依赖后续授权/任务流程在执行时再次验证当前资格。
- [并发创建绕过应用层预检查] → 以数据库唯一键作为最终约束，并将唯一键异常转换为稳定冲突错误。
- [新增顶级导航可能影响既有导航断言] → 同步修改导航规范、组件测试与 Playwright 用例，明确四项顺序及管理员可见性。

## Migration Plan

1. 新增下一编号 SQL 迁移与对应 rollback 文档，创建 `product`、`product_version` 及其约束和索引；不修改已有用户和审计表。
2. 部署后运行迁移，再发布后端 API 与前端；因新表为空，无需数据回填。
3. 回滚时先停止使用新 API，再按 rollback 文档仅在不存在下游引用和数据保留策略允许的环境中撤销新表；生产已有业务记录时不执行破坏性回滚，改为前向修复或停用入口。
