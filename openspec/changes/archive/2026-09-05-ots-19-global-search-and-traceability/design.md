## Context

参见 `proposal.md` 的 Why。当前 `vulnerability-catalog-and-workbench` 已有 `/api/v1/vulnerabilities` 的 CVE、OTS、产品、严重度、KEV、评估状态和来源时间筛选，以及 `/api/v1/vulnerabilities/{id}` 的来源、候选和当前评估入口；它固定按来源修改时间降序分页，尚无产品版本筛选、排序白名单或完整链路追溯。OTS-15/16 已在 `product_assessment` 内形成连续父子修订链，OTS-17 提供当前已批准的跨产品只读参考，因此 OTS-19 可以只组合既有 11 张表，不需要新的事实模型。

当前 NVD `1.0` 契约不提供可信 KEV/EOL 输入。用户已决定暂缓 OTS-18，并要求 OTS-19 不开展 EOL/KEV 相关任务；已有 `vulnerability.is_kev` 字段和目录基础筛选属于兼容面，本 change 不删除它们，也不以它们作为新增能力或验收数据。

## Goals / Non-Goals

**Goals:**

- 在既有漏洞目录上补齐产品版本条件、显式排序和完整 URL 状态恢复。
- 提供一次读取即可表达 CVE 当前事实、实际来源批次、候选、授权产品评估链及提交审核事件的追溯契约。
- 查询层统一应用管理员全局只读与普通用户产品版本范围，计数和节点均在裁剪后形成。
- 通过稳定分页、批量装载和索引验证满足正常规模下 95% 请求小于 3 秒。
- 只增加读取能力，不影响候选、评估状态机、修订创建或审计写入。

**Non-Goals:**

- 不实现 OTS-18 的 EOL Schema、待确认、确认/不采信、冲突处理、筛选或追溯。
- 不实现新 KEV 契约、导入、筛选、追溯、自动复评或 KEV 专项性能优化；已有字段和基础筛选保持兼容。
- 不提供任意 SQL 式查询、自定义字段、自定义排序表达式或全文搜索引擎。
- 不在追溯页编辑、提交、审核或复制评估，不替代 OTS-15 的单链修订详情和比较接口。
- 不实现 OTS-20 导出和 OTS-21 审计查询。

## Decisions

### 1. 扩展既有漏洞目录而不另建第二套全局搜索 API

继续使用 `GET /api/v1/vulnerabilities`，增加 `product_version_id`、`sort_by` 和 `sort_order`。允许的 `sort_by` 固定为 `cve_id`、`published_at`、`source_modified_at`、`cvss31_score`，`sort_order` 固定为 `asc/desc`；所有排序追加 `vulnerability.id` 同方向次序。筛选继续采用相关 `EXISTS`，确保一个漏洞只返回一行且总数不受一对多连接放大。指定 `product_id` 与 `product_version_id` 时先验证从属关系；普通用户的版本条件还必须处于有效范围。

替代方案是新增 `/global-search` 并复制现有查询逻辑，但会制造两个逐渐漂移的筛选契约和前端页面，因此不采用。搜索结果仍以漏洞为根，而不是每条产品评估一行，以保留现有导航和分页语义。

### 2. 新增以 CVE 为聚合根的窄追溯接口

新增 `GET /api/v1/vulnerabilities/{vulnerability_id}/traceability`，返回四层结构：

1. `vulnerability`：CVE、当前来源状态、关键时间和内容哈希；
2. `latest_import`：当前漏洞外键实际引用的成功导入批次非敏感摘要；
3. `candidates[]`：候选记录及其 OTS、匹配依据和首末批次；
4. `assessment_chains[]`：产品/版本/产品 OTS 与按修订号升序的 `revisions[]`。

修订节点只返回追溯所需的元数据、原因、变化摘要和提交/审核事件，不复制长篇产品结论、内部证据或跨产品参考内容；用户需要正文或版本比较时跳转 OTS-15 的已有授权接口。追溯不把 `audit_log` 当作审核来源：提交和审核事件以 `product_assessment` 修订快照为准，避免 OTS-21 审计查询成为前置依赖。

替代方案是前端串行调用漏洞详情、候选、每条评估历史和详情接口。该方案产生 N+1 请求、难以获得一致裁剪后的计数，并容易在授权变化中拼接出不同时间点的数据，因此不采用。

### 3. 使用分阶段批量查询组装追溯树

repository 在同一个只读会话中先确认漏洞可见性，再分别执行有界查询：漏洞与批次一条、可见候选一批、授权产品的全部评估修订一批。service 按候选和 `(product_ots_id, vulnerability_id)` 在内存中组装树，排序键全部显式固定。禁止为每个候选或评估循环访问数据库。

管理员候选可见性不要求已有产品评估；普通用户只有当候选能由其授权产品的当前评估支撑时才可见。评估链需包含历史修订，即使历史关联的产品版本后来停用；入口可见性仍由该用户当前有效产品版本范围决定，防止停用范围通过历史数据泄露。

替代方案是一个包含所有关系的大型 JOIN 并在应用层去重。候选、批次和修订多重一对多会产生笛卡尔放大，恶化内存、分页与计数正确性，因此不采用。

### 4. 授权裁剪先于计数和响应组装

沿用 `ScopeRepository.effective_version_ids`：管理员使用 `None` 表示全局只读，普通用户使用明确版本 ID 集。列表中的产品/版本过滤、可见性 `EXISTS`、候选计数和任务计数都复用同一范围；追溯先执行与漏洞详情一致的存在性检查，完全越权返回稳定 `403`。后续查询均带版本范围，响应中的节点计数由已裁剪集合计算。

批次本身不是普通用户可任意查询的资源，只能作为已授权 CVE 当前事实的嵌套摘要返回；本 change 不增加按批次 ID 直接追溯所有漏洞的入口。这样避免批次全局统计暴露范围外数据。

### 5. URL 是前端查询状态的来源

扩展 `VulnerabilityCatalogPage` 和 API client，把全部有效筛选、排序、页码、`page_size` 写入 Vue Router query；初始化和路由变化均从 query 解析并发起一次请求。进入追溯页时保留来源查询 URL，返回操作使用路由而不是固定目录地址。非法本地枚举不发送请求并显示参数错误；服务端仍承担最终校验和授权。

新增追溯页面按层显示加载、空组、403、404、422 和服务错误。所有外部来源文本、候选依据、修订原因和变化摘要通过 Vue 文本插值或安全 JSON 文本呈现，不使用 `v-html`。

替代方案是继续直接调用 `window.history.pushState` 并只在挂载时读取 URL；它不能可靠响应前进/后退和同组件路由变化，因此改为 Router 驱动。

### 6. 仅在 EXPLAIN 证明需要时增加索引迁移

先对现有索引执行 MySQL 8 `EXPLAIN ANALYZE`/`EXPLAIN`，覆盖默认列表、产品版本+状态、OTS+状态、严重度+时间和追溯修订查询。若执行计划或代表性数据未达门槛，再以一个编号化 SQL 迁移为既有表增加最小复合索引，并提供回滚说明、空库和升级库验证；不得新增第 12 张表。候选证据 JSON、描述等字段不做全文索引。

可能的索引候选以实测为准，包括 `product_assessment(vulnerability_id, is_current, status, product_ots_id)`、`product_assessment(vulnerability_id, product_ots_id, revision_no, id)` 以及现有连接键缺失的组合。不能仅因设计预判就写入冗余索引。

### 7. OpenAPI 契约保持窄响应和稳定枚举

为查询排序与追溯响应建立 Pydantic schema，经 OpenAPI 生成 TypeScript 类型。时间使用现有 ISO 8601 表示，变化摘要保留有界 JSON 值；不暴露 ORM 对象、绝对文件路径或完整 `manifest_json/result_json`。纯查询不调用审计服务，无论成功、校验失败、越权还是数据库失败都不写 `audit_log`。

## Risks / Trade-offs

- [追溯一次返回完整修订链，十年数据可能增长] → 当前业务键规模预期有限并要求批量查询；用代表性长链测试响应大小和耗时。若未来单链达到不可控规模，再由后续 change 为链内修订增加游标分页，不在本 change 预设复杂协议。
- [普通用户候选可见性规则与管理员不同，容易产生数量侧信道] → 所有数量由裁剪后集合计算，并用同一 CVE 同时关联授权/未授权产品的集成测试核验响应字段。
- [数据库 `NULL` 排序在升降序下表现可能不符合用户直觉] → API 契约固定使用 MySQL 当前排序语义并始终追加 ID；前端不自行重排。若验收要求 NULL 固定末尾，应在实现前统一写入契约和测试。
- [既有 KEV 筛选仍出现在旧页面，可能让人误认为数据可信] → 不删除兼容字段，但页面继续遵循“来源未启用/未提供不得推断 false”的现有语义；本 change 不新增 KEV 验收数据或功能。
- [索引增加会提高评估写入成本] → 只依据真实 MySQL 执行计划添加必要索引，并在迁移验证中回归候选生成、自动复评和评估写入。
- [追溯接口由多条 SELECT 组成，不是数据库级快照] → 单次请求复用同一短只读事务；在 MySQL 默认隔离级别下获得一致读取，并通过并发修订测试确认不返回断裂父链。

## Migration Plan

1. 先实现失败契约测试和授权/追溯集成测试，不改变数据库。
2. 扩展后端查询与追溯 API，生成 OpenAPI 与 TypeScript 类型并确认连续生成无漂移。
3. 实现 Router 驱动的目录查询和追溯页面，运行组件与系统 Chrome E2E。
4. 在代表性 MySQL 数据上执行查询计划和并发性能验证；仅在证据要求时新增编号化索引迁移。
5. 若有迁移，先验证空库安装和现有库升级，再部署后端和前端；回滚时先回滚应用，再按说明删除本 change 新增索引。无迁移时回滚仅需回退应用版本。
6. 更新 `doc/Task.md`：记录 OTS-18 因无业务输入暂缓、OTS-19 不再依赖 OTS-18、EOL/KEV 增量范围排除，并修正 ADR/风险表中的 OTS 编号错位。
