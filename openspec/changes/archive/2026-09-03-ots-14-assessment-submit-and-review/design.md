## Context

参见 `proposal.md` 的动机和范围。当前系统已有评估详情与 `PUT /api/v1/assessments/{assessment_id}/draft`，草稿保存已经执行负责人、有效产品范围、当前修订、状态和 `row_version` 校验，并在同一事务写 `audit_log`；CVSS v3.1 环境结果由服务端权威计算。`product_assessment` 已包含提交和审核全部字段，11 张应用基础表无需扩展。

需求基线是 `doc/OTS-需求规格说明-V1.6.md` 的 FR-REVIEW-001～003/005/006、FR-USER-005 和 FR-ASSESS-009/010；方案基线是提交、通过、退回事务规则；数据基线是 `doc/OTS-数据表结构-11表-V1.0.md` 第 10、11 张表。Task 将“退回动作”放在 OTS-14，但把“退回后新修订与重新提交”放在 OTS-15，本设计因此采用可明确验收的阶段边界。

## Goals / Non-Goals

**Goals:**

- 用显式动作 API 完成 `pending → submitted → completed` 主路径及 `submitted → returned` 审核决定。
- 复用既有授权、范围、环境计算、乐观锁和审计设施，在事务内冻结状态与实际操作者留痕。
- 让评估详情返回服务端计算的动作能力，使同一页面安全呈现负责人和审核人交互。
- 保持提交后修订不可被普通草稿更新覆盖。

**Non-Goals:**

- 不在退回时创建下一修订，不开放退回修改或重新提交；这些由 OTS-15 完成。
- 不处理 `reassess` 的重新提交或来源变化自动复评；分别由 OTS-15/16 完成。
- 不查询其他产品已审核摘要；FR-REVIEW-001 的这一部分由 OTS-17 完成。
- 不新增表、字段、索引、外部依赖、通知或独立批准步骤。

## Decisions

### 1. 使用三个窄动作接口而非通用状态更新

新增 `POST /api/v1/assessments/{assessment_id}/submit`、`POST /api/v1/assessments/{assessment_id}/approve` 和 `POST /api/v1/assessments/{assessment_id}/return`。三者请求都携带 `row_version`；`return` 额外携带 `review_comment`，请求模型禁止额外字段。成功统一返回扩展后的评估详情。

选择动作接口是为了把每条转换允许的来源状态、角色、字段和错误码固定在契约中，避免通用 `PATCH status` 允许跳过业务校验或夹带结论变更。替代方案是单一 `/review` 携带 decision，但独立端点更容易在 OpenAPI、审计动作和前端确认文案中保持清晰。

### 2. 服务端集中计算动作能力，动作时仍全量复核

详情响应增加 `submitted_by/submitted_at`、`review_decision/review_comment`、`reviewer_id/reviewed_at`，以及 `actions.can_submit`、`actions.can_approve`、`actions.can_return` 和稳定不可用原因。能力基于当前用户角色、有效范围、产品版本当前分配、当前修订、状态和职责分离计算；前端只负责展示。真正动作执行时重新读取并锁定上下文，不能信任页面加载时的能力结果。

替代方案是前端用角色和状态推断按钮，但它无法感知产品范围、重新分配和实际提交人变化，会造成入口与服务端不一致。

### 3. 提交使用服务端持久化快照并执行完整性门

`submit` 请求不接受草稿字段。服务在事务中读取当前评估、产品版本分配、来源 CVSS 与候选关系，完成权限和行版本检查，再对规范化后的持久化草稿执行最终完整性校验。所有业务内容字段要求非空，`applicability` 不能为 `pending`；既有条件规则继续生效。来源 v3.1 可用时，按持久化结构化指标重算并比对环境派生值；来源不可用时允许无环境分提交且保留不可用语义。

这样避免“最后一次草稿保存”和“提交”合并造成客户端同时修改内容与冻结状态，也避免客户端派生值成为提交依据。替代方案是提交完整表单快照，但会重复草稿更新逻辑并扩大并发覆盖面。

### 4. 每个状态转换采用条件更新和单事务审计

repository 以评估 ID、`is_current=1`、预期来源状态和 `row_version` 作为条件更新，并把 `row_version` 增加一。服务先做可解释校验，条件更新失败后重新读取以区分状态/当前修订/版本冲突，返回稳定 `409`；角色、范围和业务分配失败使用 `403`，字段完整性使用 `422`，审核人与提交人相同导致提交无法流转使用 `409 REVIEWER_REASSIGNMENT_REQUIRED`。

成功更新与单条 `audit_log(action=update, object_type=product_assessment)` 同事务提交。审计 detail 记录动作、修订号、状态及行版本变化和必要时间字段；退回意见只保存受长度限制的摘要或“已填写”标记，不复制完整证据和草稿。事务失败统一回滚。

替代方案是先读取后直接 ORM 修改，但仅靠应用层检查无法防止并发通过与退回同时成功。

### 5. 审核始终依据产品版本当前分配并禁止自审

审核查询通过 `product_assessment → product_ots → product_version` 获取动作时的 `reviewer_id`；评估行的 `reviewer_id` 只作为完成后的历史留痕。审核人必须具有 `reviewer` 角色、有效版本范围、等于当前分配且不等于 `submitted_by`。管理员只有同时满足这些条件才可审核。

在 `submit` 时也检查当前审核人与提交人不同，使负责人尽早得到“重新分配审核人”提示；在审核动作时再次检查，防止提交后重新分配为提交人。替代方案是只在审核时阻止，会让记录长期滞留待审核且反馈过晚。

### 6. OTS-14 的退回是只读终态，修订创建留给 OTS-15

`return` 只更新当前行的状态和审核字段，不接受产品结论字段，也不创建记录。为避免违反“已提交版本不得覆盖”，本 change 同时将既有草稿编辑授权收紧为不允许编辑 `returned`；详情仍展示退回意见并标记只读。OTS-15 必须从这条退回修订复制业务快照创建下一修订、切换 `is_current`，随后再开放新 `returned` 修订编辑和重新提交。

该取舍严格遵守 Task 的 change 边界，但意味着 OTS-14 交付后退回记录不能立即修改。替代方案是在 OTS-14 创建下一修订，会提前实现 OTS-15 的核心职责；直接编辑同一退回行则会破坏提交快照。

### 7. 前端在既有详情页按状态呈现单一主操作区

负责人在可提交草稿上看到“提交审核”，确认框汇总冻结与不可再编辑提示；审核人在 `submitted` 详情看到只读审核区和“通过/退回”，退回对话框提供必填意见。请求期间禁用同类动作；成功后完全采用响应刷新表单、行版本、状态和留痕。`422` 映射字段，重新分配错误给出管理员操作提示，`403` 显示权限/分配已变化，`409` 提示刷新，其他错误保留对话框输入并允许重试。

路由仍使用 `/system/assessments/:assessmentId`。不新增专用审核页面，以满足评估和审核使用同一详情页并减少上下文切换。

## Risks / Trade-offs

- [OTS-14 退回后暂不可修改，用户可能认为流程中断] → 页面明确提示“已退回，等待创建新修订”；OTS-15 作为强依赖下一 change，不在本 change 隐式实现修订。
- [现有测试或页面假定 `returned` 可编辑] → 先增加失败测试并同步调整详情 `editable`、草稿保存状态集合和提示，保证提交快照不被覆盖。
- [提交完整性字段定义过严影响现实草稿] → 以 Task 和 FR-ASSESS-006/012 的“最终提交前完整”为准，返回全部字段路径；不把来源缺失的 CVSS 当作负责人可修复错误。
- [提交校验与草稿校验漂移] → 复用同一规范化与条件校验函数，提交层只增加完整性、状态和环境一致性门。
- [审核重新分配引发页面能力过期] → 动作时实时复核并用 `403/409` 稳定错误提示刷新，不缓存业务分配。
- [并发动作写入不同结果] → 条件更新包含状态和行版本，并用 MySQL 集成测试验证只有一个动作提交。

## Migration Plan

1. 先更新后端 OpenAPI 请求/响应模型和契约测试，再实现 repository 条件更新、服务校验与路由。
2. 更新前端生成类型、详情动作区域及组件测试，最后补系统 Chrome Playwright 主路径与异常路径。
3. 本 change 不修改数据库结构；部署只需按常规顺序升级后端和前端。发布前确认现有 `returned` 数据将显示为只读。
4. 回滚应用版本即可移除动作接口与 UI；已成功提交或审核的数据属于有效业务历史，不自动反向改写。若业务要求回退状态，须通过经审计的数据修复方案另行审批，不使用迁移脚本删除留痕。
