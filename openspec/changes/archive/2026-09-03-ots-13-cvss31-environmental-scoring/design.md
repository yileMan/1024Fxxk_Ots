## Context

参见 `proposal.md` 的动机，以及两个 delta spec 的行为约束。OTS-12 已提供 `GET /api/v1/assessments/{assessment_id}` 和 `PUT /api/v1/assessments/{assessment_id}/draft`，使用当前负责人、有效产品范围、可编辑状态和 `row_version` 保护完整草稿保存，并在实际变化时同事务写 `audit_log`。现有响应只包含核心草稿和来源 CVSS 只读摘要，环境评分字段尚未进入契约。

`product_assessment` 已具有 `cvss_version`、`environmental_score`、`environmental_vector`、`cvss_metrics_json` 和 `calculator_version`；`vulnerability` 已具有当前采用的 v3.1 分数、严重度、向量和来源。因而本 change 必须复用现有 11 张应用基础表，不增加迁移。需求基线为《OTS 信息维护平台需求规格说明》V1.6 的 FR-MASTER-007、FR-ASSESS-005、FR-VULN-002/003，方案基线为《OTS 信息维护平台系统方案》V1.6 第 6 章，数据基线为《OTS 信息维护平台数据表结构（11 表）》V1.0。

## Goals / Non-Goals

**Goals:**

- 建立单一、确定、可独立回归的 CVSS v3.1 解析与环境分数计算核心。
- 让既有评估草稿资源保存结构化指标，并由服务端生成所有派生字段。
- 让前端即时预览与后端权威结果使用相同测试向量和清晰的未保存状态语义。
- 无迁移地使用既有字段，并保持 OTS-12 的授权、乐观锁、幂等和审计保证。

**Non-Goals:**

- 不实现 CVSS v4.0、版本自动协商、v3.0 向量升级或无来源向量时的推断。
- 不改变评估状态机，不实现提交、审核、修订创建、自动复评或导出。
- 不修改 NVD 包格式和来源评分采用优先级；非法来源向量的修复属于导入质量治理。
- 不把 CVSS 分数解释为适用性、产品影响或处置结论。

## Decisions

### 1. 采用项目内纯函数计算核心并固定兼容标识

在后端建立无数据库依赖的 CVSS v3.1 模块，输入为来源完整基础向量和结构化环境指标，输出为规范化指标、完整环境向量及单小数分数。解析器只接受 `CVSS:3.1`，要求八个基础指标各出现一次，拒绝未知、重复、缺失和非法值；计算实现严格遵循 FIRST v3.1 公式、Modified Scope 下的 `MPR` 权重、影响上限及 Roundup 规则。

`calculator_version` 使用代码常量，例如 `ots-cvss31-1`，含义是本平台算法兼容版本而非依赖包版本。任何公式或规范化规则变化都必须更改该标识并补回归测试。选择项目内小型纯函数实现，是因为 v3.1 公式范围有限、需要精确控制十进制舍入和错误语义；替代方案是直接采用第三方库，但会引入版本、舍入实现和离线依赖审计风险。实施前仍可先检索现有锁定依赖是否已有充分验证的实现，只有其官方示例、边界舍入和许可证均满足时才复用。

### 2. 来源基础指标不可编辑，环境覆盖使用闭合集合

来源向量提供 `AV/AC/PR/UI/S/C/I/A`。产品草稿仅保存 `CR/IR/AR/MAV/MAC/MPR/MUI/MS/MC/MI/MA`，每个键都有固定允许值，`X` 表示未定义并回退到对应来源基础指标或规范默认权重。持久化 JSON 使用全部 11 个键的规范顺序和大写短码，避免缺键与 `X` 两套语义造成无变化保存误判。

本 change 不开放 Temporal 指标 `E/RL/RC`。它们不是 Task.md 所要求的产品环境指标，来源当前标量也未保存 Temporal 采用值；把它们加入产品表单会扩大业务决策范围。计算环境分数时按 v3.1 默认 `X` 权重处理。替代方案是让前端提交完整环境向量，但字符串重复了来源基础指标，容易产生矛盾和篡改，因此只接受结构化环境指标。

### 3. 扩展既有详情和完整草稿 PUT，不增加独立评分写接口

评估详情新增评分区：来源 v3.1 原始字段、`environmental_scoring.available`、不可用原因，以及已保存的 `metrics/score/vector/calculator_version`。无来源向量时 `available=false`，派生结果返回空，不尝试从来源分数或严重度还原基础指标。API 不增加或返回任何 v4.0 字段。

既有 `PUT .../draft` 请求增加 `cvss_metrics`。客户端不需要也不应提交分数、向量、`cvss_version` 或计算器版本；Pydantic 继续禁止额外字段，使篡改请求稳定返回 `422`。服务在校验来源和指标后调用计算核心，并把五个评分持久化字段合并到 OTS-12 的同一条件更新。选择扩展完整草稿 PUT 可保证核心字段与环境指标只有一个版本基线和事务；独立 `/cvss` 写接口会造成两个保存按钮、两个 `row_version` 流程及部分成功状态。

### 4. 评分字段作为一个一致性组处理

只要来源可用且请求包含规范化环境指标，服务端总是同时设置 `cvss_version='3.1'`、结构化指标、环境分数、完整向量和计算器版本。全部指标为 `X` 仍是合法评分：它表示没有产品覆盖，环境公式回退到来源基础指标，而不是“未评分”。无来源 v3.1 才是不可评分状态，此时保存环境指标返回字段级 `422 CVSS31_SOURCE_UNAVAILABLE`，不会清空或写入部分字段。

当前来源若在页面加载后变化，保存事务按最新 `vulnerability.cvss31_vector` 计算；响应返回实际采用的来源向量。这样不信任陈旧客户端来源。OTS-16 将负责来源实质变化后的复评修订，本 change 不改变修订生成规则。替代方案是要求客户端回传来源向量或时间戳，但这仍不能成为权威来源，且增加契约状态。

### 5. 复用 OTS-12 原子更新、幂等比较和审计

规范化后的环境指标和服务端派生字段加入旧值比较与单条条件更新，条件仍包含评估 ID、当前修订、可编辑状态、负责人和 `row_version`，保存前仍重新校验有效产品范围。核心草稿和评分组任一变化都只递增一次版本；全部规范化值无变化时不更新 `updated_at` 或审计。

审计 `changed_fields` 增加评分字段；详情记录变化的指标键、分数前后值、向量哈希或摘要、计算器版本及行版本，不复制完整来源事实，也不记录客户端声称的派生字段。计算异常和数据库异常均回滚业务行与审计。复用现有事务而非建立单独评分审计，可保持一次用户保存对应一条原子业务意图。

### 6. 前端使用本地纯计算预览，但服务端结果始终覆盖

评估详情页在当前产品结论区展示只读来源评分和环境评分区。来源可用且详情 `editable=true` 时，表单显示 11 个指标选择；变更后由前端纯计算模块即时预览，并标记“未保存预览”。保存仍通过完整草稿 PUT，仅发送指标和核心字段；成功后用响应整体重置表单、版本基线和已保存结果。

前后端实现共享同一组 FIRST 官方与边界 JSON 测试夹具，而不是共享运行时代码：这避免浏览器依赖后端请求才能预览，同时用契约测试锁定一致性。若预览异常，页面显示无法预览但允许用户修正；任何保存失败保留指标输入。并发冲突沿用 OTS-12 的刷新确认流程，不自动重放或覆盖本地选择。只读修订展示其历史保存结果和计算器版本，不用当前算法静默重算历史。

### 7. 分层验证官方示例、边界和纵向安全行为

计算核心测试覆盖 FIRST 官方示例、全部指标枚举、`X` 回退、Modified Scope、`MPR` 权重、零影响、10 分上限及易错 Roundup 边界。API/服务测试覆盖无来源、非法来源、未知/v4.0 指标、额外派生字段、权限、范围撤销、只读状态、无变化和双 session 冲突；MySQL 测试确认 JSON、`DECIMAL(3,1)`、审计和回滚。

前端组件测试覆盖来源提示、可编辑/只读指标、预览标签、保存回填、字段错误和冲突输入保留。Playwright 按项目约定使用系统 Chrome，覆盖负责人从待办进入、修改指标、预览、保存和重新加载，以及无来源和篡改请求不能形成结果。OpenAPI 连续生成必须一致，新增代码覆盖率不低于 80%。

## Risks / Trade-offs

- [手工公式在十进制边界与 FIRST 结果偏差] → 使用十进制运算或等价的整数 Roundup 策略，以官方示例和专门构造的临界值双端回归。
- [前后端双实现产生预览漂移] → 共享数据夹具并把服务端响应作为唯一最终值；CI 同时运行两端向量测试。
- [来源向量在编辑期间变化] → 保存始终读取事务内当前来源并在响应回显；客户端预览只标为未保存，来源变化后的复评由 OTS-16 处理。
- [既有数据库允许 `cvss_version='4.0'`] → 所有 V1 API schema 和 service 只生成 `3.1`，响应白名单不暴露 v4.0；不为收紧检查约束新增迁移。
- [全部 `X` 被用户误解为没有评分] → 页面文案说明其为“未覆盖来源指标”，仍展示按来源基础指标计算的环境结果；真正无来源时使用独立不可用状态。
- [历史记录由旧计算器生成] → 详情展示持久化结果和 `calculator_version`，不在读取时重算；算法升级通过新版本标识和后续修订处理。

## Migration Plan

1. 不执行数据库迁移；先建立后端计算核心和官方向量失败测试，再完成解析、校验与计算。
2. 扩展评估详情/草稿 schema、service、repository 映射和审计，在单元、API 与 MySQL 集成测试通过后重新生成 OpenAPI 与 TypeScript 类型。
3. 增加前端计算预览模块和评估详情评分区，运行 Vitest、类型检查和生产构建。
4. 使用系统 Chrome 完成 Playwright 纵向验收，并运行全量相关回归、覆盖率检查、需求追溯及 OpenSpec 严格校验。

回滚只需回退本 change 的后端、生成契约和前端代码，无数据库结构回滚。已保存的 v3.1 指标与派生字段保留在既有列中；旧应用不会编辑或展示它们，但后续重新部署可继续读取，禁止通过回滚脚本删除用户已保存的评估数据。
