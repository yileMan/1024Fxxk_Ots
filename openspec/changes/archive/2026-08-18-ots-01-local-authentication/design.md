## Context

参见 `proposal.md` 的变更动机和 `specs/local-authentication/spec.md` 的行为契约。当前仓库只有最小 FastAPI/Vue JavaScript 骨架；本设计以 `ots-00-platform-foundation` 已完成并归档为实施前提，复用其 MySQL 连接、编号迁移执行器、后端分层、统一错误响应、Vue 3 TypeScript 基础、API client、路由和测试框架。

认证遵循需求规格 V1.6 的本地账号边界、系统方案 V1.6 的低成本基础安全方案、数据表结构 V1.0 的 `app_user`/`audit_log` 定义以及 Task ADR-04。V1 仍限制为 11 张应用基础表，不增加会话、刷新令牌、登录日志或密钥表。

## Goals / Non-Goals

**Goals:**

- 建立后续接口可复用的当前用户认证依赖，同时确保状态和角色以数据库当前值为准。
- 以最少服务端状态完成两小时固定会话、停用即时失效和同源写请求保护。
- 固定初始化管理员、密码摘要、Cookie 配置、错误码、前端恢复流程和失败处理。
- 为 `app_user`、`audit_log` 提供符合 11 表基线的迁移与回滚路径。

**Non-Goals:**

- 不在认证层实现角色权限矩阵或产品范围授权；后续 change 在当前用户依赖之上叠加授权。
- 不提供单会话撤销、多设备管理、滑动续期、刷新令牌或登录风控。
- 不为 OTS-00 缺失的工程基础提供临时替代实现。

## Decisions

### 1. 实施以 OTS-00 归档为硬门槛

OTS-01 开始实现前检查 `ots-00-platform-foundation` 已归档且其测试、构建、MySQL 迁移执行器和前后端 TypeScript/API 基线可用。这样保持 Task.md 规定的单向依赖，避免认证 change 同时承担平台重构。

替代方案是把缺失基线合并进 OTS-01，但会扩大变更、模糊验收并导致后续能力依赖一个混合 change，因此不采用。

### 2. 使用基线中的两张表，不保存服务端会话

编号化迁移按数据表结构 V1.0 原样创建 `app_user` 和 `audit_log`，包括类型、唯一键、索引、状态约束、角色 JSON 约束与外键。`app_user` 是认证唯一数据来源；`audit_log` 本阶段只完成结构，不接入认证流程。

不增加 session 表、撤销表、缓存或 `session_version` 字段。这样满足 11 表限制和 ADR-04，但接受退出只能清除当前浏览器 Cookie 的限制。

### 3. Argon2id 摘要与单一密码服务

密码服务使用成熟库生成包含参数与随机盐的 Argon2id 编码摘要，并用同一入口执行校验。初始化管理员要求密码长度为 12～256 个字符；后续 OTS-02 创建或重置密码时复用同一策略。登录输入也限制最大长度，避免异常大输入消耗资源。摘要参数以测试环境可覆盖、生产环境使用安全默认值的配置提供。

初始化管理员命令接收登录名和显示名称，密码优先从无回显交互读取，也允许从专用环境变量读取以支持部署自动化；不接受把密码作为普通命令行参数。命令在单个事务中按唯一登录名检查并创建，已存在时不修改任何字段。

替代算法 bcrypt 也能满足基础要求，但 Argon2id 对现代密码存储更合适且无需兼容历史摘要，因此采用 Argon2id。

### 4. Cookie 保存签名最小载荷

认证 Cookie 建议命名为 `ots_session`，载荷只包含版本、用户 ID、签发时间和固定过期时间，不包含角色、状态、显示名称或密码信息。使用服务端密钥对完整载荷签名；用户 ID 不属于机密信息，因此不增加加密层。认证依赖依次完成签名/时效校验、用户查询和状态检查。

会话固定两小时，不因请求而续期。Cookie 使用 `HttpOnly`、`SameSite=Lax`、`Path=/` 和对应 `Max-Age`/`Expires`；正式 HTTPS 环境必须启用 `Secure`，本地 HTTP 开发配置可以关闭。签名密钥由环境配置注入，生产环境缺失或强度不足时应用拒绝启动；更换密钥会使全部现有 Cookie 失效。

替代方案包括数据库会话和刷新令牌。前者违反本次无会话表约束，后者增加令牌存储、轮换和撤销复杂度，均不采用。

### 5. 三个认证 API 与稳定失败语义

API 使用统一 `/api/v1` 前缀：

| 接口 | 成功结果 | 主要失败 |
| --- | --- | --- |
| `POST /api/v1/auth/login` | `200`，返回公开用户信息并设置 Cookie | `AUTH_INVALID_CREDENTIALS` |
| `POST /api/v1/auth/logout` | `204`，幂等清除 Cookie | `AUTH_ORIGIN_REJECTED` |
| `GET /api/v1/auth/me` | `200`，返回数据库当前用户信息 | `AUTH_SESSION_INVALID`、`AUTH_USER_DISABLED` |

登录时，未知账号、密码错误和已经停用统一返回 HTTP 401 与 `AUTH_INVALID_CREDENTIALS`，降低账号枚举风险。已持有效 Cookie 的用户随后被停用时返回 HTTP 403 与 `AUTH_USER_DISABLED`，供前端给出明确反馈。缺失 Cookie 视为未登录；过期、篡改或指向不存在用户的 Cookie 返回 HTTP 401 与 `AUTH_SESSION_INVALID`，同时清除 Cookie。

登录成功在同一事务中更新 `last_login_at`，但不调用审计服务。公开用户响应只包含 `id`、`login_name`、`display_name` 和 `roles`。

### 6. 使用 Origin 校验控制 Cookie 写请求

认证中间件或依赖对携带认证 Cookie 的 `POST`、`PUT`、`PATCH`、`DELETE` 校验 `Origin`。登录和退出接口也强制校验来源，因为它们会设置或清除认证 Cookie。允许来源从单一管理平台公开地址配置，执行规范化后做完整 scheme/host/port 比较，不使用后缀或子串匹配。缺少或不匹配时在业务逻辑前返回 HTTP 403 与 `AUTH_ORIGIN_REJECTED`。

本项目采用同源部署，因此不增加双提交 CSRF Cookie、服务端 CSRF 状态或跨域凭据配置。确需无浏览器调用时使用明确配置的可信来源执行，不通过放宽全局规则实现。

### 7. 前端仅在内存中保存当前用户

前端认证状态保存公开用户信息和初始化状态，不把身份、角色或 Cookie 复制到 `localStorage`/`sessionStorage`。应用启动或首次进入受保护路由时只调用一次 `/auth/me` 恢复身份；并发导航复用同一个初始化请求。

路由守卫保存经过校验的站内目标路径，登录成功后返回该路径；外部 URL 或协议不得作为回跳目标。全局 API 错误处理在收到认证错误时清空内存状态并导航到登录页：会话无效显示“会话已失效”，停用显示“账号已停用”。退出无论服务端是否已有 Cookie 都清空本地状态。

### 8. 认证日志与审计分离

登录、退出、`/auth/me` 和 `last_login_at` 更新不写 `audit_log`。应用日志只记录事件类型、结果、时间和内部关联 ID；不得记录请求密码、密码摘要、完整 Cookie、签名密钥或完整登录请求体。若未来需要登录历史或来源地址追踪，应另行提出安全日志 change，而不是复用数据库变更审计表。

## Risks / Trade-offs

- [复制的 Cookie 在用户退出后仍可使用至两小时到期] → 缩短固定有效期；敏感情况下由管理员停用用户或轮换签名密钥使其立即失效。若业务要求单会话撤销，另行修订 ADR 和数据基线。
- [签名密钥轮换会让全部在线用户退出] → 把轮换安排在维护窗口并在发布说明中告知；V1 不为无中断轮换增加多密钥机制。
- [每次请求查询用户增加一次数据库读取] → 当前仅 10～20 个并发用户，按主键读取成本可接受，并换取停用和角色变化实时生效。
- [两小时固定到期可能中断长时间编辑] → 前端明确提示会话失效；不在本 change 引入续期机制，后续可基于实际使用反馈单独评估。
- [`SameSite=Lax` 不能替代完整 CSRF 防护] → 所有 Cookie 写请求额外执行严格 Origin 校验，并保持管理平台同源部署。
- [XSS 仍可代表用户发起同源请求] → 依赖 OTS-00 的安全响应头和前端转义基线；HttpOnly 只保护 Cookie 不被脚本直接读取。

## Migration Plan

1. 确认 `ots-00-platform-foundation` 已归档，并在空库和升级测试库中验证迁移执行器。
2. 执行下一个连续编号的迁移，先创建 `app_user`，再创建引用它的 `audit_log`；校验恰好新增两张基线表及全部约束、索引。
3. 配置 Cookie 签名密钥、管理平台允许来源、Cookie Secure 模式和 Argon2id 参数；生产配置不合规时阻止启动。
4. 部署后端认证接口和前端登录链路，再通过无回显交互或专用环境变量运行初始化管理员命令。
5. 执行登录、停用实时失效、Cookie 安全属性、同源拒绝、无审计记录和端到端场景验证。

回滚时先停止应用，删除 `audit_log` 后删除 `app_user`，再回退认证路由和前端入口。该回滚会删除已创建的用户数据，只允许在首次上线验收失败且尚未产生业务引用时执行；一旦后续表引用用户，应采用向前修复，不执行破坏性回滚。
