## Context

现有仓库仅有最小 FastAPI 与 Vue 3 JavaScript 工程。后续 change（从 `ots-01-local-authentication` 起）需要共享的 API 前缀、错误契约、数据库迁移、TypeScript 类型和测试入口。动机及能力边界见 `proposal.md`；可验证行为见本 change 的四份 delta spec。

平台遵循单体应用、单节点 MySQL 的 V1 约束。迁移采用 ADR-01 的编号化 SQL，不采用 Alembic；本 change 不创建 11 张应用基础表中的任何业务表。前端和 API 同源部署，外部采集服务与本平台仅通过后续离线文件契约交换数据。

## Goals / Non-Goals

**Goals:**

- 固定后端 `api/routes`、`schemas`、`services`、`repositories`、`models` 分层及 `/api/v1` 路由前缀。
- 使空库环境能够执行迁移、启动服务，并让管理端健康页可观察应用与 MySQL 状态。
- 建立单一 OpenAPI → TypeScript 类型生成路径，防止前后端接口模型漂移。
- 为后续 change 提供可复用的真实 MySQL、组件和浏览器验证命令与 80% 新增代码覆盖率门槛。

**Non-Goals:**

- 不创建 `app_user`、`audit_log` 或任一业务基础表；它们由 OTS-01 及后续 change 的连续迁移创建。
- 不交付认证、授权、业务页面、后台队列、缓存、消息队列、外网访问或外部数据服务。
- 不引入 Alembic、Redis、RabbitMQ、微服务、对象存储或独立搜索引擎。

## Decisions

### 1. 以最小分层单体固定后端边界

在 `backend/app` 下建立 `api/routes`、`schemas`、`services`、`repositories`、`models` 和基础设施模块。路由只处理 HTTP 输入输出与依赖注入；服务层编排事务和业务规则；Repository 仅负责数据访问；Schema 是 OpenAPI 的输入输出来源。健康检查可直接使用数据库基础设施，但不得绕过统一错误和日志中间件。

统一错误体至少包含 `code`、`message`、`correlation_id`；请求中间件生成或接收安全格式的关联标识并写入结构化日志。生产配置缺少必填秘密时拒绝启动；响应与日志均做字段级脱敏。选择这一模式是为了让 OTS-01 的认证和后续审计写入有稳定位置，而不把业务规则堆进路由。替代的“单一 app 文件”会使后续模块缺少清晰事务与契约边界，因此不采用。

### 2. 健康检查采用依赖探测而非静态存活

`GET /api/v1/health` 返回服务与数据库两个离散状态。数据库探测使用受限、只读的连接检查和短超时；成功返回 HTTP 200，数据库不可用返回非成功状态及机器可读状态。接口不需要认证，但禁止返回异常、主机、数据库名或凭据。

仅返回“进程仍在运行”的 liveness 接口无法满足 `doc/Task.md` 的健康页验收，故不采用。把健康状态写入表会引入无价值的业务数据与同步问题，也不采用。

### 3. 迁移以编号 SQL 和独立迁移元数据实现

迁移文件位于 `backend/migrations/`，命名为连续编号的 `NNN_description.sql`，并为每个文件提供同编号回滚说明或受控回滚脚本。迁移执行器以专用元数据记录已成功版本、校验信息和执行时间；它不是 OTS 业务表，也不得被业务 Repository 使用。执行器一次只运行一个待执行脚本：脚本成功后才在同一数据库事务内登记版本；失败立即停止且不登记成功。

应用通过 SQLAlchemy 提供连接池、会话/事务单元；业务写入由服务层显式提交或回滚。选择此方式以满足 ADR-01 的可移植升级包与“不创建 `alembic_version`”约束。Alembic 自动迁移、启动时隐式建表和 ORM 自动建表都会降低 SQL 可审阅性，因此不采用。

### 4. 前端一次性迁移为 Vue 3 + TypeScript 管理端壳

前端保留 Vite 与 Vue 3，迁移源文件、测试和配置至 TypeScript，并选定一个支持 Vue 3 的管理端组件库用于布局、导航、反馈和表单的后续复用。路由提供默认入口、健康页和未找到页；应用根提供全局通知出口。

从后端导出的 OpenAPI 文档生成 API 类型和 client 输入输出模型；生成产物受版本控制或由可重复命令生成，并在验证中检查漂移。统一 API client 解析标准错误体和网络错误，并把可展示反馈交给通知层，避免页面各自解析异常。手写前端 DTO 虽可快速开始，但会在后续认证和业务接口变化时产生契约漂移，故不采用。

### 5. 测试按失败优先的四层质量门禁组织

后端以 pytest 运行单元与真实 MySQL 集成测试；前端以 Vitest 运行组件测试；Playwright 运行前后端联通的健康页冒烟。测试数据库通过专用环境变量和名称隔离，迁移测试覆盖空库、重复执行及失败中止；不得指向开发或生产库。覆盖率分别在前端与后端命令中强制检查新增代码不低于 80%。

保留每个层级单独执行的命令，以缩短开发反馈，同时提供完整验证顺序供 CI 或发布前运行。仅使用 Mock 数据库会遗漏迁移、驱动和事务问题，因此不作为集成测试替代。

### 6. 开发配置与文档只提供非秘密模板

`.env.example` 列出数据库地址、测试数据库、日志级别、前端 API 基址与未来秘密配置的变量名和格式要求，不填入真实凭据。开发说明记录依赖安装、环境变量、迁移、启动、类型生成和验证命令。OpenSpec 文档固定以 capability 的 kebab-case 目录命名；change 只有在 strict validation、构建和测试证据齐备后才能归档。

## Risks / Trade-offs

- [真实 MySQL 集成测试需要本地或 CI 服务] → 使用独立测试连接配置，在依赖缺失时明确失败；不得回落到开发库。
- [MySQL DDL 对事务支持有限，失败脚本可能留下部分对象] → 每份迁移提供经过审阅的回滚说明，执行器不登记失败版本，并在升级测试库演练恢复。
- [OpenAPI 类型生成增加一次构建步骤] → 将生成和漂移检查纳入标准命令，换取后续接口变更的早期发现。
- [健康检查暴露数据库状态] → 只返回有限状态枚举，不暴露内部地址、异常或凭据。
- [Vue JavaScript 到 TypeScript 的迁移会产生初始改动面] → 仅迁移平台壳与现有最小入口，不在本 change 预建业务模块。

## Migration Plan

1. 在隔离开发环境补齐后端和前端依赖、环境模板、分层目录与测试脚本；不改动数据库业务数据。
2. 部署迁移执行器与空迁移/验证迁移，在空 MySQL 和升级测试库中验证编号、重复执行、失败停止与回滚说明。
3. 部署后端运行时和健康接口，先验证数据库可用与不可用两种响应，检查日志和响应未泄露秘密。
4. 部署 TypeScript 管理端壳与健康页，生成 API 类型后运行组件测试、构建和 Playwright 冒烟。
5. 通过严格 OpenSpec 校验及全部质量门禁后归档本 change，OTS-01 才可创建 `app_user` 与 `audit_log` 迁移。

若前端部署失败，可回退至上一静态前端构建；若后端运行时部署失败，可回退应用版本。迁移机制验证阶段不承载业务数据；一旦后续业务迁移已依赖其元数据，只能通过新的向前修复迁移处理问题，不删除迁移记录或业务数据。
