## Why

OTS-10 只在管理员执行候选匹配时处理候选依据变化，尚不能识别 CVE 状态、CVSS、KEV 或产品 OTS 上下文的独立实质变化；已完成评估因此可能继续基于过期事实，进行中评估也缺少可见的变化提醒。OTS-16 需要在不覆盖历史结论和用户输入的前提下补齐统一、幂等的自动复评闭环。

## What Changes

- 建立规范化的复评基线与变化分类：比较 CVE 状态、CVSS v3.1、受影响范围、KEV、OTS/CVE 候选依据及产品 OTS 上下文，忽略描述、引用、批次时间等非实质文字或来源元数据变化。
- 在漏洞导入/候选执行和产品 OTS 关联新增、停用或恢复的既有事务中同步计算受影响的产品评估；有历史引用的关联改为受控停用而非物理删除，不新增轮询任务、消息队列、通知表或第 12 张业务表。
- 对当前 `completed` 评估原子保留旧修订并创建单一 `reassess` 当前修订，继承产品结论作为复评起点、清空提交审核事件，并保存稳定原因、结构化变化摘要和新基线。
- 对 `pending`、`returned`、`reassess`、`submitted` 当前修订不创建并行修订、不覆盖用户内容；合并新的未处理变化提示，使负责人或审核人能在当前流程中看到事实已变化。
- 使用稳定的变化指纹和已处理基线保证同一变化重复导入、重试或从不同入口到达时不重复创建修订；并发写入只能形成一次状态变化和一条受限审计。
- 扩展工作台和评估详情：待复评卡片继续实时读取当前修订，详情显示复评原因、字段级变化摘要、父修订旧结论对比及重新提交入口；不发送邮件或站外通知。
- KEV 规则只在后续包格式实际提供 KEV 数据时生效；本 change 不启用 OTS-09、不改变 NVD `1.0` 包契约，也不实现 EOL 复核。
- 覆盖 FR-VULN-005、FR-MATCH-005、FR-REVIEW-004、FR-WORK-001 和系统方案 5.5；依赖已归档的 OTS-10 与 OTS-15。

## Capabilities

### New Capabilities

- `automatic-reassessment`: 定义实质变化分类、状态相关处理、基线与幂等、事务审计、负责人站内待办及变化摘要展示。

### Modified Capabilities

- `assessment-task-generation`: 将现有仅处理候选执行直接变化的复评规划扩展为可复用的统一变化分类，并规定进行中修订的变化合并行为。
- `assessment-revision-and-resubmit`: 将自动来源变化纳入统一修订创建原语，并为自动复评原因、变化摘要、历史对比和重新提交补充契约。
- `ots-bom-management`: 为产品 OTS 关联补充可恢复状态；新增、停用或恢复关联时同步生成缺失任务或触发相关自动复评，并与关联和审计原子提交。

## Impact

- 后端：漏洞导入、候选匹配、产品 OTS 关联写服务，评估修订服务与 repository，变化规范化/指纹计算、审计摘要，以及相关 FastAPI schema 和 OpenAPI。
- 前端：工作台待复评提示、评估详情的自动复评原因与变化摘要、旧结论对比和重新提交状态反馈，以及生成的 TypeScript 类型。
- 数据：在既有 `product_assessment` 补充最小评估基线、指纹和变化摘要，在 `product_ots` 补充可恢复状态与乐观锁；继续复用现有内容哈希、修订原因和审计能力，不新增基础表。
- 测试：后端单元与 MySQL 事务/并发/幂等测试、OpenAPI 漂移检查、前端 Vitest 与系统 Chrome Playwright 纵向验收，并验证纯文字变化、Rejected、CVSS、范围、候选、KEV 条件数据和产品 OTS 新增关联矩阵。
