## Context

参见 `proposal.md` 的动机和 `specs/automatic-reassessment/spec.md` 的行为契约。当前 OTS-10 只在候选执行事务中比较旧/新候选，并直接为 `completed` 创建 `reassess`；它没有把来源 CVSS、状态、KEV 或产品上下文保存为每条评估的稳定基线。OTS-15 已提供受锁保护的修订克隆、连续父子链、历史与比较 API、`returned/reassess` 编辑重提和单一 current 约束，但自动修订仍由 OTS-10 的另一套复制代码创建。

需求基线是 `doc/OTS-需求规格说明-V1.6.md` 的 FR-VULN-005、FR-MATCH-005、FR-REVIEW-004、FR-WORK-001，方案基线是 5.2、5.3、5.5、7.3 和 8.1～8.3，数据基线是 `doc/OTS-数据表结构-11表-V1.0.md` 的 `product_ots`、`vulnerability`、`vulnerability_ots_match`、`product_assessment` 与 `audit_log`。本设计仍使用 11 张应用基础表，不引入外网连接、独立任务/通知表或异步基础设施。

## Goals / Non-Goals

**Goals:**

- 用一套规范化基线与差异引擎覆盖来源导入、候选匹配和产品 OTS 关联三个写入口。
- 统一 OTS-10 与 OTS-15 的修订创建原语，保证历史不可变、状态安全、幂等、并发和事务一致性。
- 让进行中修订安全感知新事实，并以 `row_version` 阻止用户基于过期来源视图继续写入。
- 使有历史的产品 OTS 关联可以受控停用和恢复，从数据模型上表达“关联变化”且不破坏外键历史。

**Non-Goals:**

- 不启用或定义 OTS-09 的 KEV/EOL 输入包；KEV 比较代码只消费已经由有效契约写入的字段，缺失不推断。
- 不处理 EOL 日期/状态复核、跨产品参考、全局追溯或评估导出；分别保留给 OTS-18、17、19、20。
- 不因产品/版本说明、负责人、审核人、产品状态或普通来源文字变化自动复评；人员调整继续使用既有实时分配规则。
- 不自动修改产品适用性、环境评分、影响或处置结论，也不自动撤回 `submitted`。

## Decisions

### 1. 在第 10 表保存每条修订的最小评估基线

新增编号化迁移 `013_automatic_reassessment.sql` 及回滚说明，在 `product_assessment` 增加三个可空字段：

- `assessment_basis_sha256 CHAR(64)`：规范基线 JSON 的稳定 SHA-256；
- `assessment_basis_json JSON`：只保存复评判断需要的规范字段，不复制描述、完整引用或产品结论；
- `reassess_changes_json JSON`：保存有界字段级变化摘要、稳定类型和触发时间，历史修订保留只读。

基线 JSON 固定 `schema_version=1.0`，按稳定键顺序编码以下分区：`source`（规范状态、CVSS v3.1 分数/向量、受影响范围、条件 KEV）、`candidate`（存在性、匹配方式、规范范围证据）和 `product_context`（`product_ots_id`、关联状态）。缺失候选与未启用 KEV 使用显式的“不可用”语义，不能和 `false` 混同。差异摘要最多保留固定条目数，长值保存安全截断显示值与摘要哈希；完整事实仍从第 8/9 表读取。

选择持久化规范快照而不只保存 `content_sha256`，因为现有漏洞总哈希包含描述等非实质字段，且候选更新后无法仅靠当前表重建变化前值。选择在既有评估表增加字段而不是新建事件表，可满足 11 表约束并让每条历史修订自带当时基线。代价是存在受控的 JSON 数据冗余，需用 schema 版本和上限约束。

### 2. 产品 OTS 使用软状态表达有历史的关联变化

同一迁移为 `product_ots` 增加 `status VARCHAR(16) NOT NULL DEFAULT 'active'`、限定 `active|disabled` 的 CHECK 和 `row_version INT NOT NULL DEFAULT 1`。没有下游历史的关联仍可物理删除；已有 `product_assessment` 引用时，移出当前清单改为条件更新 `status=disabled`，恢复时复用同一关联 ID，避免删除外键历史或绕过 `(product_version_id, ots_component_id)` 唯一键。

所有采集范围、当前清单、任务生成和候选到产品的展开只读取 `active`；管理员历史视图可显式包含 `disabled`。新增关联为当前候选创建缺失 `pending`；停用/恢复为该 `product_ots` 已有的各 CVE 当前评估生成或合并 `PRODUCT_OTS_DISABLED/PRODUCT_OTS_RESTORED` 变化。没有历史的物理删除不可能影响评估，因此不创建复评。

保留现有 `DELETE` 仅处理无历史物理删除；新增 `POST /api/v1/product-versions/{version_id}/ots/{relation_id}/disable` 和 `/restore`，请求只含 `row_version`。CSV 导入只新增 `active` 关联；遇到同业务键的 `disabled` 关联报告稳定冲突并引导显式恢复，避免文件上传静默恢复历史关系。替代方案是删除后重建关系，但会被外键阻止或切断历史；仅把变更写审计则无法实时生成正确采集范围和任务。

### 3. 单一差异引擎以“旧基线—目标基线”规划操作

新增独立领域服务负责规范化、哈希、字段级 diff 和状态决策，供导入、候选及 OTS 服务调用。调用方必须在修改来源/候选/关联前提供旧值，在同一事务构造目标事实并锁定相关业务键的当前评估。操作分类固定为：

- 无当前评估且目标关联与候选有效：创建 `pending`，直接保存目标基线，不产生“复评”；
- 当前为 `completed` 且指纹变化：调用统一克隆原语创建 `reassess`；
- 当前为 `pending/returned/reassess/submitted` 且指纹变化：保持状态和业务字段，只更新基线、合并变化摘要并递增 `row_version`；
- 指纹相同：`unchanged`，零评估写入和零复评审计。

变化类型按字段白名单生成，不信任来源总哈希。规范化受影响范围和候选证据复用 OTS-08 的版本比较语义并稳定排序；CVSS 分数以十进制定点语义比较，向量先解析并按固定指标顺序输出；状态大小写和约定空值规范化；KEV 只有输入契约明确提供时才进入基线。

采用规划后应用而不是在 ORM 更新后回看，可以同时生成预览、实际结果和审计，且避免旧事实丢失。所有入口提交前重新计算，不能信任前端预览。

### 4. 来源导入先处理现有关系，候选执行补齐集合差异

确认导入的批次事务在第 8 表 upsert 前取得旧漏洞事实，并对该 CVE 当前候选关联到的产品评估比较来源分区。CVSS、状态、KEV 或范围实质变化会立即创建/合并复评；纯描述变化只更新漏洞事实。范围变化此时不会猜测新的候选集合。

随后管理员执行既有 OTS 匹配时，服务用同一目标基线替换候选分区，处理候选新增、更新和移除。来源入口已记录的相同范围字段因目标指纹一致不会重复；候选存在性或证据带来的额外差异会合并到当前摘要。候选、任务、批次结果和审计仍保持 OTS-08/10 的原事务边界。

选择两阶段协作而不是把全量匹配强塞进文件导入，可保留当前“导入后由管理员预览并执行匹配”的产品流程和性能边界；代价是范围变化到匹配执行之间，负责人先看到来源范围变化，候选集合变化稍后补充，但不会重复修订。

### 5. 自动修订复用 OTS-15 克隆原语

把 `assessment_editor` 的字段白名单克隆和 `assessment_tasks` 的自动 `_reassessment` 合并为 repository/service 级统一原语。调用方传入父修订、期望状态/行版本、当前负责人、原因类型、目标基线和变化摘要；原语统一完成当前行条件降级、下一修订号、业务字段复制、事件字段清空、子行插入和审计。

自动子修订的 `owner_id` 取产品版本当前负责人，并再次校验其启用状态与 `product_owner` 角色。负责人不可用时整个触发事务失败并返回稳定 `OWNER_UNAVAILABLE`，防止来源已更新而复评丢失。人工修订继续使用原负责人授权入口，退回修订继续保存退回事件语义。

手工 `reassess_reason` 仍为不超过 500 字的可读摘要；稳定原因类型不再通过扫描审计猜测，而由 `reassess_changes_json.trigger_type` 或人工/退回路径直接序列化。这样避免历史审计量增长导致详情查询退化。

### 6. 进行中变化采用行版本冲突而非状态跳转

对进行中修订更新基线与变化摘要时，使用 `assessment_id + is_current + expected status + row_version` 条件更新并将行版本加一。保存、提交、审核与自动变化竞争时只有一个成功；失败方重新读取后重算，自动处理若发现已覆盖则为 `unchanged`，用户动作则沿用 `409` 刷新提示。

合并规则以规范字段路径为键：同一字段多次变化保留“当前修订基线起点的 before”和最新 after；值回到起点时移除该变化项；不同字段稳定排序并受数量上限约束。该设计保护用户正文且让最终审核看到累计未处理差异。替代方案自动把 `submitted` 退回复评会伪造审核动作并打断工作流；新建并行修订会违反单一 current。

### 7. API 和前端在现有详情上增加窄字段

评估详情和修订摘要增加 `reassessment` 对象：`trigger_type`、`triggered_at`、`basis_sha256`、`change_types`、`changes` 和 `truncated_count`；历史详情只读返回该修订当时的对象。既有修订比较 API继续比较产品业务字段，前端在同一页面另以“来源/候选/产品上下文变化”卡片展示自动摘要，并可跳到父修订产品结论对比。

工作台计数和任务列表无需新接口，仍实时读取 `status=reassess`。待审核详情若存在提交后变化摘要，在审核按钮前显示高优先级提示；按钮仍由服务端动作能力控制。所有变化值按不可信纯文本渲染，不使用 `v-html`。`401/403/409/422` 沿用当前统一处理；失败不丢失草稿或关联页面上下文。

### 8. 原子性、审计与性能边界

每个入口固定按产品 OTS/CVE 业务键排序后锁定，避免批量处理死锁。来源/候选/关联业务写、评估基线或修订、入口结果摘要和 `audit_log` 同事务提交。审计只保存入口、批次或关联 ID、受影响数量、变化类型计数、父子 ID/修订号和基线指纹，不保存完整前后值、证据或产品正文。无变化、权限拒绝和冲突重算不写审计。

批量查询必须按漏洞、OTS 和产品关联集合加载，禁止逐评估 N+1。沿用 10,000 CVE 性能样本，并补充代表性多产品展开、变化摘要内存和产品 OTS 批量导入测试；目标是不降低既有五分钟离线处理上限，正常工作台和详情查询继续满足现有索引路径。

## Risks / Trade-offs

- [规范基线规则以后变化可能把等价数据判成变化] → 基线携带 `schema_version`，版本升级必须提供迁移/重建策略和固定回归样本，不能静默更换算法。
- [在 `product_assessment` 保存来源快照产生冗余] → 只保存复评字段、使用有界 JSON 和摘要哈希，不复制描述、引用、完整证据或产品正文。
- [来源导入因一个负责人不可用而回滚，影响批次可用性] → 在预览中提前统计 `OWNER_UNAVAILABLE` 并阻止确认，管理员先修复人员分配；不能用跳过换取来源与评估不一致。
- [软停用改变原先有历史关联的删除体验] → 保留无历史物理删除，历史关联改用明确停用/恢复确认并默认从当前清单隐藏；采集范围与任务查询统一过滤状态。
- [自动更新 `row_version` 会打断正在编辑或审核的用户] → 这是防止基于过期事实提交的安全冲突；前端保留本地输入、展示变化并让用户刷新后重试。
- [同一范围变化分两阶段到达导致摘要更新两次] → 使用单一基线指纹和字段路径合并；只有新增候选差异才产生第二次受限更新，不创建第二修订。
- [历史详情扫描审计判断原因类型会随数据增长变慢] → 原因类型与变化摘要随修订持久化，停止用审计反查自动/人工类型。

## Migration Plan

1. 新增 `013_automatic_reassessment.sql` 和回滚说明，为两张既有表添加上述字段、CHECK/索引并保持应用基础表总数为 11；先在副本验证 MySQL 8.4 JSON、默认值和锁行为。
2. 部署只读兼容代码后运行一次受控基线初始化：按业务键稳定分页，为所有当前评估从当前来源、候选和关联状态生成 `assessment_basis_json/sha256`，不创建复评、不改业务结论并记录迁移摘要。初始化完成前保持三个自动触发入口关闭写入。
3. 部署差异引擎、统一克隆原语、来源/候选/关联事务集成及 OpenAPI；再部署生成类型和前端变化卡片、关联停用/恢复交互。抽样核对纯文字、CVSS、Rejected、范围、候选、关联停用/恢复和多产品独立性后启用写入口。
4. 回滚应用前停止导入、匹配和产品 OTS 写入。已产生的基线、变化摘要和修订都是有效业务历史，不删除或合并；旧应用若不认识 `disabled` 关联或新字段，不得直接恢复流量，应部署兼容版本。
5. 仅当尚未启用自动触发且确认没有新状态/基线依赖时，才可按回滚说明删除新增列。启用后回滚只停止触发逻辑并保留列与数据，任何历史数据清理必须另行审批。
