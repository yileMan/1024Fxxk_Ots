## Context

当前系统已由 OTS-03 提供 `product`、`product_version`、管理员鉴权、同事务审计和产品建档向导前两步，但尚无 OTS 与产品清单数据层。实现必须同时遵循 `doc/OTS-需求规格说明-V1.6.md`、`doc/OTS-系统方案-V1.6.md` 和 `doc/OTS-数据表结构-11表-V1.0.md`：新增内容只能落入既定第 5 张表 `ots_component` 和第 6 张表 `product_ots`，不得用额外状态、导入暂存或历史表绕开基线。动机见 [proposal.md](proposal.md)，可观察行为见 `specs/ots-bom-management/spec.md` 和 `specs/product-version-management/spec.md`。

需求规格 FR-MASTER-001 中“停用 OTS”的笼统表述与详细数据基线存在冲突。本变更按已确认的取舍严格遵循 11 表基线：OTS 没有 `status`，不提供停用或删除；产品版本不再使用某 OTS 时移除 `product_ots` 关联，已有下游历史时保留关联。

## Goals / Non-Goals

**Goals:**

- 使用既定两张表交付 OTS 主数据和产品版本/OTS 多对多关联，不改变 11 表数量与字段边界。
- 使单条维护与 CSV 批量导入共享唯一性、冲突、权限、审计和事务规则。
- 形成可供 OTS-06 采集范围实时查询、可供 OTS-10 产品评估引用的稳定关联标识。
- 将现有产品建档流程安全扩展至第 3 步，允许前两步已保存后单独重试清单维护。

**Non-Goals:**

- 不实现 OTS 状态、OTS 删除、人员分配、独立导入批次或清单版本历史。
- 不实现 SPDX、CycloneDX 等标准 SBOM 导入，也不为历史 CSV 提供自动列映射。
- 不生成采集范围，不处理外部 ZIP 数据包、漏洞候选匹配、产品评估或产品范围授权。
- 不引入后台队列；清单 CSV 在一次 HTTP 请求和数据库事务内完成校验与写入。

## Decisions

### 严格映射第 5、6 张基础表

新增下一编号 SQL 迁移和对应 rollback 文档，按数据基线创建 `ots_component(id, ots_name, ots_version, official_website, is_eol, row_version, created_at, updated_at)` 与 `product_ots(id, product_version_id, ots_component_id, created_by, created_at, updated_at)`。建立 `uk_ots_name_version`、`uk_product_version_ots`、既定普通索引和三项外键，不增加状态、软删除或 CSV 暂存字段。

该方案保证后续查询路径和 11 表验收一致。替代方案是在 OTS 增加 `status` 或为导入创建暂存/历史表；前者违背已确认的数据基线，后者突破 11 表约束，因此不采用。OTS 是否“在用”由启用产品、启用产品版本及 `product_ots` 关联共同决定。

### 由数据库唯一键兜底，服务层统一规范化和历史保护

创建或编辑 OTS 时在服务层对名称、版本去除首尾空格，并依赖数据库排序规则处理大小写；先做友好预检查，最终以 `uk_ots_name_version` 抵御并发重复。编辑使用 `row_version` 条件更新。关联创建以 `uk_product_version_ots` 兜底，移除前检查 `product_assessment` 等下游引用；有引用时返回稳定冲突，不删除关联。

选择服务层校验加数据库约束，是为了同时提供字段级反馈和并发正确性。仅做应用预检查存在竞态；数据库触发器会隐藏业务规则并偏离现有分层，均不采用。虽然 OTS-04 实施时产品评估表可能尚未创建，保护逻辑仍以外键约束与可扩展的引用检查表达，并在后续建表后回归验证。

### 使用资源化 JSON API 和独立 CSV 端点

建议 API 组织如下，最终字段以 OpenAPI 为唯一契约：

- `/api/v1/ots-components`：分页查询与创建；`/{ots_id}`：详情和带 `row_version` 的编辑；`/{ots_id}/product-versions`：关联产品版本只读查询。
- `/api/v1/product-versions/{version_id}/ots`：当前清单查询和单条关联创建；`/{product_ots_id}`：受保护移除。
- `/api/v1/product-ots/template`：空白模板下载。
- `/api/v1/product-versions/{version_id}/ots/import`：CSV 原子导入。
- `/api/v1/product-versions/{version_id}/ots/export`：当前清单导出。

所有端点复用管理员依赖。JSON 错误继续使用项目既有错误详情结构，区分未找到、字段校验、唯一冲突、历史引用冲突和乐观锁冲突；CSV 导入错误返回结构化的 `row`、`field`、`reason`，供前端直接展示。选择独立端点而非复合“保存建档”端点，可使版本维护和向导第 3 步复用同一契约，并避免清单失败回滚已保存的产品和版本。

### 固定最小 CSV 契约并执行两阶段原子导入

CSV 使用 UTF-8，读取时兼容可选 BOM；固定且完整的表头顺序为 `ots_name,ots_version,official_website,is_eol`，其中 `is_eol` 使用规范布尔文本。模板与导出使用相同表头，不包含数据库 ID，从而允许在环境间由业务键识别 OTS。

导入分为两个内存阶段：第一阶段只解析并校验表头、编码、文件限制、必填字段、布尔值、行内与跨行重复，再批量读取数据库中命中的 OTS/关联并生成全部错误；存在任一错误即返回，数据库无写入。第二阶段在单一事务中创建缺失 OTS、复用字段完全一致的已有 OTS并补充缺失关联；已有业务键但官网或 EOL 不一致视为人工主数据冲突，不做自动更新。整个事务成功后追加一条 `batch_upsert` 汇总审计，失败则全部回滚。

选择“创建缺失、复用一致、拒绝冲突”的规则，可以让清单导入完成实际建档，同时满足人工冲突不得静默覆盖。仅接受 OTS ID 会使模板依赖环境内部标识；无条件 upsert 会覆盖人工主数据；逐行提交会产生部分清单，均不采用。已有且已关联的相同行作为幂等项报告，不算错误；同一文件内重复业务键则报告后续重复行，帮助清理输入。

### 单条写入逐对象审计，批量导入汇总审计

单条 OTS 创建、编辑、关联添加和允许的关联移除分别追加对应 `insert`、`update` 或 `delete` 审计；CSV 成功导入只追加一条 `batch_upsert`，记录产品版本、文件名及新增 OTS、新增关联、已存在数量，不为每行生成审计。业务写入和审计使用同一事务。查询、模板、导出、被拒请求和回滚不写审计。

该做法符合第 11 表关于批量写入的约束，并避免大清单产生无意义的审计膨胀。审计详情不保存完整 CSV 或敏感文件路径。

### 前端复用同一清单组件完成向导和版本维护

新增仅管理员可见的“OTS”一级导航和 OTS 管理页，提供分页筛选、创建/编辑、关联产品版本查看以及加载、空、错误和并发冲突状态。工作台沿用现有卡片设计并补齐产品管理、OTS 主数据、用户与角色、服务状态四个入口，不另建视觉体系。产品版本详情和建档向导第 3 步复用同一清单组件，支持选择已有 OTS、受控移除、模板下载、CSV 导入与导出。

向导按步骤持久化：前两步沿用 OTS-03 已有 API；第 3 步只操作已创建版本的关联。第 3 步失败时保留产品 ID、版本 ID、选择和文件错误上下文，允许重试或退出后从版本维护继续，不执行补偿删除。这样避免用跨多个请求的伪事务导致已成功主数据被破坏。

### 本变更不引入业务状态机

`ots_component` 没有状态，`product_ots` 仅表示关联存在与否，因此不设计额外状态机。`is_eol` 是 OTS 生命周期事实，不代表停用；修改它走普通乐观锁更新。关联移除是否允许由下游历史引用决定，而不是通过隐藏状态表达。

## Risks / Trade-offs

- [FR-MASTER-001 的“停用 OTS”无法在 11 表详细基线中表达] → 记录已确认的基线优先取舍，以关联存在性表达实际使用范围，并在需求追溯中标明偏差。
- [CSV 业务键命中但其他字段不一致可能阻塞整批导入] → 返回全部行/字段冲突，要求管理员先在 OTS 管理页明确修改主数据或修正 CSV，禁止隐式覆盖。
- [单请求原子导入占用内存和事务时间] → 沿用平台文件大小和行数限制，先完成无写入校验，再使用批量查询与批量插入；V1 规模按约 200 个 OTS 设计，不引入后台队列。
- [并发导入或单条创建可能在预检查后产生唯一键竞争] → 数据库唯一键作为最终裁决，将异常转换为稳定冲突并整体回滚。
- [未来产品评估创建后，原本可移除的关联将受保护] → 移除服务始终执行引用检查；后续创建 `product_assessment` 的变更补充真实外键集成测试，不改变本变更 API 语义。
- [编辑共享 OTS 会影响多个产品版本展示] → OTS 详情明确显示关联产品版本，编辑前提示其为共享主数据；继续使用乐观锁防止静默覆盖。

## Migration Plan

1. 新增下一编号 SQL 迁移和 rollback 文档，按基线创建 `ots_component`、`product_ots`、外键、唯一键和索引；验证应用基础表总数按阶段增加但最终仍以既定 11 表为上限。
2. 运行空库与从 OTS-03 数据库升级的迁移验证，再发布模型、仓储、服务、API 和 OpenAPI 生成契约。
3. 发布前端 OTS 页面、清单组件及建档向导第 3 步；新表为空，无需数据回填。
4. 回滚应用时先停用新路由和页面。仅在不存在业务数据及下游引用的非生产环境按 rollback 文档先删除 `product_ots`、再删除 `ots_component`；已有业务数据的环境不执行破坏性回滚，采用前向修复并保留主数据和关联历史。
